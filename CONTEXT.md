# 领域词汇表

## observability（可观测性）扩展分类

第 8 个扩展顶层分类（`extensions/observability/`），归集以「观测/分析 pi 自身（插件、工具、skill、会话）的运行与效果」为核心目的的插件。

**observability / 可观测性**：
对 pi 自身的插件、工具、skill、会话进行采集 → 存储 → 分析 → 展示的横切能力（含运行遥测、静态清单、有效性评估三类）。
_避免_：telemetry（遥测，仅指采集一环）、monitoring（监控，偏告警）

_边界_：`meta/` 基础设施（pi-logger、pi-config、pi-lab、pi-session-tree 等）不迁移，保持最底层约束；首批仅迁入 `session-analytics`（原 `tui/session-breakdown`，见 ADR-0030）。

## pi-lab 实验框架

| 术语                                        | 定义                                                                                                                                                                                                                                    |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Experiment / 实验**                       | 一个 A/B 测试实例，包含多个臂（arm）、分配策略（strategy）和反馈记录（outcome recording）                                                                                                                                               |
| **Arm / 臂**                                | 实验中的一种变体方案（如 `classic` 精确匹配 vs `row-script` 模糊行匹配）                                                                                                                                                                |
| **Allocation Strategy / 分配策略**          | 选择臂的算法。默认稳定哈希分桶（哈希空间按 arm 权重切分，默认等权）；bandit（Thompson Sampling / Epsilon-Greedy）为 opt-in 在线优化模式                                                                                                 |
| **Stable Hash Bucketing / 稳定哈希分桶**    | 分配策略之一：用稳定哈希（用户/会话 ID）决定 arm，保证同一主体跨试次稳定落在同一 arm，避免实验内漂移                                                                                                                                    |
| **Outcome / 反馈信号**                      | 一次实验试次的执行结果，为 `{ armId, metrics: { metricId: number }, metadata? }`；不设固定字段，测什么由实验声明的 metric 决定                                                                                                          |
| **Consumer / 消费方**                       | 通过 pi-lab API 注册实验并在自身逻辑中调用 select/record 的插件（如 edit）                                                                                                                                                              |
| **GlobalThis Bridge / globalThis 桥接**     | pi-lab 通过 `globalThis.__labApi` 暴露 API，消费方通过鸭子类型访问，不依赖模块导入的解耦模式                                                                                                                                            |
| **Deferred Registration / 延迟注册**        | 消费方不在模块初始化时注册实验，而是推迟到 `session_start` 或首次 execute 的时序安全点再进行                                                                                                                                            |
| **Degradation / 降级**                      | 当 pi-lab 不可用时，消费方静默回退到无实验模式的兜底行为                                                                                                                                                                                |
| **Load-Order Hazard / 加载顺序竞险**        | 消费方在模块初始化时同步检查全局桥接，但 pi-lab 尚未加载导致注册错失的时序问题                                                                                                                                                          |
| **Registration Owner / 注册方身份**         | 实验注册时由消费方显式声明的身份 key（`ExperimentDef.owner: string`）。pi-lab 仅以 `(owner, name)` 二元组判定两个注册是否属于同一逻辑实验，不解释 owner 的命名/层级语义（是否用插件名、是否编码 user/project 级别，均由消费方自行决定） |
| **Owner Conflict / 异主冲突**               | 两个不同 owner 声明同一实验名的硬冲突。撞名是配置错误而非竞争：后声明者被阻断，不覆盖已有实验                                                                                                                                           |
| **Definition Evolution / 定义演进**         | 同 owner 重声明时采集口径（实验臂、指标、分配策略、上下文键）发生变化。原地更新定义并告警「历史数据口径不一致」的副作用                                                                                                                 |
| **Idempotent Re-registration / 幂等重注册** | 同 owner 且口径未变的重声明（如跨会话重复注册）。静默复用已存在实验，不产生任何事件                                                                                                                                                     |

### pi-lab 职责边界（2025 年确认）

pi-lab 是**纯基础设施**——提供测量、存储、统计分析。**不做决策。**

| API        | 职责   | 说明                                                                                                                  |
| ---------- | ------ | --------------------------------------------------------------------------------------------------------------------- |
| `select()` | 分配   | 按实验注册时声明的分配策略返回 armId。默认稳定哈希分桶（按 arm 权重切分，默认等权）；不做自动选臂（bandit 为 opt-in） |
| `record()` | 写入   | 接收结构化多指标 outcome，append 到 JSONL 时序事件流。插件决定报什么值                                                |
| `query()`  | 分析   | 返回各 arm 在某 metric 上的贝叶斯后验结论（均值、credible interval、胜出概率、guardrail 告警）。插件决定用不用        |
| `info()`   | 元数据 | 返回实验配置、arms、metrics 定义                                                                                      |

**决策归属**：smart-context（或其他消费方）根据 `query()` 返回的分析结论，自己判断是否切换 arm、什么时候切换、按哪个指标判断。pi-lab 不替插件做决策。

### 实验方法论（2026-02 确认）

| 术语                              | 定义                                                                                                                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A/A Self-check / AA 自检**      | 验证分流/测量/模型无偏的内置能力：假臂对照（两臂指向同一实现，跑一段看胜出概率是否 ~50/50）+ SRM 检查（实际两臂样本量是否偏离 1:1）。贝叶斯形式为后验校准（AA 后验应收敛到无差异） |
| **Capability Variant / 能力变体** | A/B 实验臂的一般形态——能力的参数/策略变体（工具集切 or 参数切），区别于「扩展开关」（装/卸扩展是环境级变更、非会话内变体，排除在 pi-lab 之外）                                     |

### 实验形态分类学（2026-08 确认）

把「能力变体」进一步按**实验形态**与**臂来源**两个正交维度细分，回答「这个维度该用 select 还是 record、臂从哪里来」。

| 术语                                             | 定义                                                                                                                                                                                                        |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Experiment Form / 实验形态**                   | A/B 实验的干预方式二分类：select 型（框架随机分流、比客观指标）vs record 型（用户主动选、只统计满意度）。                                                                                                   |
| **Select-type Experiment / select 型（分流型）** | 随机分流比客观指标的实验形态。`select()` 随机（stable-hash）分臂，`record()` 报客观指标（如 `match_success`、`saved_tokens`）。适合「用户对该维度无明确偏好、可安全随机分流」的场景。                       |
| **Record-type Experiment / record 型（记录型）** | 用户主动选配置、pi-lab 只统计满意度不干预选择的实验形态。注册臂 = 用户可选配置项，只 `record()` 不 `select()`。适合「用户有明确偏好」的场景（用户主动选 preset/mode 即明确意图，pi-lab 不该替用户随机切）。 |
| **Arm Source / 臂来源**                          | A/B 臂从哪来：代码实现变体（同一逻辑的不同实现）vs 配置状态变体（配置载体插件的配置状态本身当臂）。                                                                                                         |
| **Implementation Variant / 代码实现变体**        | 臂 = 同一能力的多种代码实现（edit 的 `classic` 精确匹配 vs `row-script` 模糊行匹配）。                                                                                                                      |
| **Configuration State Variant / 配置状态变体**   | 臂 = 配置载体插件的配置状态本身（preset id / mode id / 工具范围档位），无需另写实现代码。                                                                                                                   |
| **Form Selection Criterion / 形态选择判据**      | 用户对该维度有无明确偏好 → 有偏好走 record（不干预）、无偏好走 select（可随机分流）。                                                                                                                       |

**P0/P1 插件到形态的映射**：

| 插件              | 实验名                 | 形态   | 臂来源               | 臂                        |
| ----------------- | ---------------------- | ------ | -------------------- | ------------------------- |
| edit              | edit-strategy          | select | 代码实现变体         | `classic` / `row-script`  |
| custom-compaction | profile-satisfaction   | record | 配置状态变体         | profile id                |
| smart-context     | compression-aggression | select | 配置状态变体（参数） | `balanced` / `aggressive` |
| tools             | tool-range             | select | 配置状态变体         | `core` / `full`           |
| preset            | preset-usage           | record | 配置状态变体         | preset id                 |

### Metric 定义

| 术语                          | 定义                                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Metric / 观测指标**         | 插件在注册实验时声明的测量维度，含 id、type、direction（maximize/minimize）及信号来源与聚合方式（对哪个源、哪个字段、何种聚合）           |
| **Metric Type**               | `binary`（是/否）、`continuous`（数值）、`count`（次数）                                                                                  |
| **Guardrail Metric**          | 非目标指标的副作用监测指标（如工具报错率），确保实验不损害基础体验                                                                        |
| **Composite Score**           | 多个原始 metric 加权合成的单一标量，用于程序自动决策时判断 arm 优劣。属消费方领域逻辑，不是 pi-lab 基础设施                               |
| **Derived Metric / 派生指标** | 由原始 metric 经声明式聚合（如 weighted-sum / any-fail）计算出的指标；权重声明在实验配置（注册时默认 + 用户可覆盖），`query()` 时投影计算 |
| **Outcome Recording**         | 每轮记录 `{ armId, metrics: { metricId: number, ... }, metadata?: {...} }`                                                                |

### 信号采集

| 术语                                   | 定义                                                                                                                                                                                                                                                      |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ingestion Source / 信号入口**        | 产生实验事件的四条通道：① `record()` API 同步直报；② 会话树 TAG（插件主动打标 / 规则自动打标，经 pi-session-tree 接口读取，直接读会话文件兜底）；③ pi-log 结构化日志解析（`[pi-lab-signal]` 行）；④ 被动信号源（订阅 pi-logger `log` 总线，免消费方埋点） |
| **Signal Adapter / 信号适配器**        | 把各信号入口的原始格式（label 字符串、日志行、lifecycle 事件）解析成统一 Event 的解析器。TAG、日志、lifecycle 三个标准 adapter 内建，另开放 `registerIngestionSource(name, extractor)` 扩展点                                                             |
| **Passive Signal Source / 被动信号源** | pi-lab 内建信号源的**总称**，下辖两类：生命周期信号（push）与行为信号（pull）。形态为点对点（采集 → ingest），不对外广播——多组件订阅能力由 pi-logger `log` 总线本身承担                                                                                   |
| **Lifecycle Signal / 生命周期信号**    | 被动信号源之一。pi 原生执行事件（tool/message/turn/agent/session，统称 lifecycle）的投影（isError、duration、usage），**push 语义**（事件发生即 emit）。由 pi-logger 结构化（`__lifecycle__` details），pi-lab 内建适配器采集；通用、无实验语义           |
| **Behavioral Signal / 行为信号**       | 被动信号源之一。从会话树结构与用户行为推断的指标（回退、纠正、重复修改），**pull 语义**（turn_end 主动检测）。由 pi-session-tree 出基础原语、各插件实现领域语义                                                                                           |

### 信号归因

| 术语                                     | 定义                                                                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Turn-level Attribution / turn 级归因** | 被动信号按 turn 聚合，归因到该 turn 内活跃实验的活跃臂（实验 `select` 时登记，`turn_end` flush）                       |
| **Shared Observation / 共享观测**        | token 等全局指标属 turn 级观测，被多个活跃实验共享（允许跨实验重复归因），以 `metadata.turnId` 作观测键供未来去重/聚合 |

### 存储

| 术语                          | 定义                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Event Stream / 时序事件流** | append-only JSONL 文件（每实验一个），每行一条 outcome 事件 `{ ts, armId, ctxKey, metrics, metadata }` |
| **Context Key / 上下文键**    | 事件上的普通字段（非存储分桶键），如 model 标识；`query()` 时可任意按此维度聚合                        |
| **Projection / 投影**         | `query()` 时从事件流动态计算聚合视图（后验参数、均值、胜出概率），而非读预先物化的计数                 |

### 统计分析

| 术语                                | 定义                                                                                                                    |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Bayesian Posterior / 贝叶斯后验** | 用共轭先验（binary→Beta、continuous→Normal-Gamma、count→Poisson-Gamma）对 metric 数据做推断，结论形态为概率而非 p-value |
| **Win Probability / 胜出概率**      | `P(arm i 在所有臂中表现最好)`，由后验分布蒙特卡洛采样估算，供消费方做切换判断                                           |
| **Credible Interval / 可信区间**    | 贝叶斯后验的区间估计（如 95% HDI）；不同于频率学派的置信区间                                                            |
| **Guardrail Alert / 护栏告警**      | guardrail metric 显著恶化（如 P(恶化)>0.95）时触发的告警，不参与选赢家，只做副作用监测                                  |

### Outcome 信号评分模型

| 信号               | 类型       | 评分                 | 时序         |
| ------------------ | ---------- | -------------------- | ------------ |
| 回退到之前节点     | binary     | →1（坏）             | 异步（事后） |
| detectRetry        | binary     | →1（坏）             | 异步         |
| fork 分支          | binary     | →1（坏）             | 异步         |
| 纠偏（同分支修正） | count      | →0.5（坏）           | 异步         |
| 继续 1-2次         | continuous | +1（好）             | 异步         |
| 继续 3-5次         | continuous | 0（中性）            | 异步         |
| 继续 >5次          | continuous | →1（坏，模型太啰嗦） | 异步         |
| 工具报错率 > 10%   | binary     | →1（坏）             | 同步（本轮） |

综合：`composite_score = Σ signals` → >0 success, <0 failure, =0 neutral

## bench 评测体系（离线配对基准）

移植自 pi-fabric 的 DeepSWE 风格 paired benchmark，为「某个插件是否带来可量化的边际价值」提供离线评测。与 pi-lab 互补：pi-lab 管会话内变体，bench 管环境级装/卸扩展（见 ADR-0026）。

| 术语                                         | 定义                                                                                                                                                                                                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **离线配对基准（Offline Paired Benchmark）** | 固定任务 + 固定模型下，对比「无插件 vs 有插件」两个配置臂的边际价值。_避免_：基准测试（benchmark 泛指）、离线 A/B                                                                                                                                          |
| **评测单元（Cell）**                         | 一次 `(task, config, rep)` 三元组的独立运行，产出 `result.json`。                                                                                                                                                                                          |
| **任务（Task）**                             | 一个真实 repo 改动任务的完整定义 = 三件套。_避免_：场景、用例                                                                                                                                                                                              |
| **任务三件套（Task Trio）**                  | `task.json`（repo URL + base_ref + 超时）+ `prompt.txt`（给 agent 的原始提示）+ `verify.sh`（验收探针）。                                                                                                                                                  |
| **配置臂（Config Arm）**                     | 一次对比中的一个环境配置：`无插件` vs `有插件`（单插件 + 其依赖链）。在「臂注册表」登记为实体（臂名 → 该臂被测插件注册的工具名）。_避免_：config 组、实验臂（那是 pi-lab 术语）                                                                            |
| **臂注册表（Arm Registry）**                 | `bench/arms.json`——评测环境的单一来源：公共基座（`baseline`，非被测变量）+ 全部配置臂。**臂封闭**：未登记的臂 fail-fast。_避免_：插件清单、config 列表                                                                                                     |
| **先导门（Pilot Gate）**                     | 全量评测前的门：每个臂 × 第一个任务 × rep0 先跑一遍即停下，人工判断后再 `--resume` 继续。与全量同属一个 run（`manifest` 写全量配置），故先导的 cell 可被复用。_避免_：预检、前置检查（那是本机环境自检）、冒烟门槛（那是案例入库门槛）                     |
| **验收探针（Verify Probe）**                 | `verify.sh`，从任务验收标准机械推导，输出 `reward_binary` / `reward_partial`。                                                                                                                                                                             |
| **边际价值（Marginal Value）**               | 有插件 vs 无插件在同一 task 上的度量 delta（解决率 / token / 成本 / 耗时 / 行为）。插件有效性的唯一口径。_避免_：绝对达标、功能正确性                                                                                                                      |
| **插件触发生效（plugin_triggered）**         | 独立指标，标记「有插件」臂里目标插件是否被实际调用（工具名由**臂注册表**声明）。未触发的 cell 不混入边际价值 delta，单列触发率。                                                                                                                           |
| **冒烟门槛（Smoke Gate）**                   | 案例入库前的双向检查：无/有两臂各跑一次，任一维度出现可观测 delta 才入库；`verify.sh` 必须能正常执行产出 reward。                                                                                                                                          |
| **前置检查（Preflight）**                    | 跑任何 cell 之前的门：对本次 run 的**本机**前置条件做**纯自检**（模型存在、工具链可用、本地依赖就位），缺失即 fail-fast；不预热、不安装、不查远端可达性（见 ADR-0056）。_避免_：环境初始化、依赖预热、远端探测、冒烟门槛（后者是案例入库门槛，非每次运行） |
| **评测模型（Bench Model）**                  | 冒烟用 mock-llm（不烧钱、验证 verify.sh 双向判定）；真实**强制显式** `--model <provider>/<model-id>`（无默认值，preflight 校验存在于 models-store）。成本从 session jsonl 的 `usage.cost` 读取，不 hardcode 费率。                                         |
| **运行标识（Run ID）**                       | 一次矩阵评测的唯一标识，形如 `run-YYYYMMDD-HHMMSS`，即 `bench/results/<run-id>/` 目录名。启动与结束都显式打印，报告/进度/日志都挂在它下面。                                                                                                                |
| **后台评测运行（Background Bench Run）**     | 长耗时 bench 的运行模式：`nohup` 后台启动，用户通过「问进度」触发查询与反馈，而非同步阻塞等结果。                                                                                                                                                          |
| **进度查询（Progress Query）**               | 通过 `bench-status.sh <run-id>` 读 `progress.json` + `run.log` 回答「跑到哪了 / 还剩多少 / 哪些失败」。                                                                                                                                                    |
| **进度文件（progress.json）**                | `results/<run-id>/progress.json`，结构化记录总量/已完成/失败 + 每个 cell 的 `pending                                                                                                                                                                       | running | done | failed | skipped`状态与阶段（`clone | agent | metrics | verify`）。 |
| **运行日志（run.log）**                      | `run-matrix.sh` 自身 stdout+stderr 全量 tee 到 `results/<run-id>/run.log`，后台跑也能留档审计。                                                                                                                                                            |
| **断点续跑（Resume）**                       | `--resume <run-id>`：跳过已完成 cell（`result.json` 含 `reward_binary`），中断/残缺 cell 重跑；配置不一致拒绝续跑。语义对齐上游 Harbor `job resume`（见 ADR-0031）。                                                                                       |

## pi-session-tree 会话树查询服务

| 术语                                | 定义                                                                                                                                                                        |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Session Tree / 会话树**           | Pi 的 `SessionManager` 以 append-only tree 结构管理会话历史——每个 entry 有 id/parentId/timestamp，支持分支、回滚。pi-session-tree 封装此原始树为可查询的接口。              |
| **SessionTreeNode / 会话树节点**    | pi-session-tree 的自有抽象，封装 Pi 原生 SessionEntry 并附加计算字段（depth, branchIndex），隔离 Pi 版本变化。                                                              |
| **Tree Query Service / 树查询服务** | pi-session-tree 的核心定位——提供 8 类查询（节点、路径、结构、聚合、内容、窗口、标注、快照），不包含业务决策逻辑。                                                           |
| **Path / 路径**                     | 从根节点到某个节点的链（祖先链）。核心查询包括 pathToLeaf()、pathBetween()、distance()、LCA()。                                                                             |
| **Branch / 分支**                   | 当用户从某个 entry 回滚并发送新 prompt 时，该 entry 获得多个子节点形成分支。branchCount() 统计分叉点数。                                                                    |
| **Tree Complexity / 会话复杂度**    | 基于 branchCount × maxDepth × compactionCount 的加权综合指标，供应用层判断是否需要切换复杂模型。                                                                            |
| **Annotation / 标注**               | pi-session-tree 通过 `Pi.appendEntry()` 将计算结果（如复杂度分、上下文快照）以 CustomEntry 写回会话树，跨 `/reload` 持久化。                                                |
| **Snapshot / 快照**                 | 轻量快照（leafId + entry 计数），供 diff() 检测自上次查询以来的增量变化。                                                                                                   |
| **Primitive / 基础原语**            | pi-session-tree 提供的稳定、通用、无实验语义的会话树结构查询（`isDescendant`/`detectDiverge`/`pathToLeaf`/`analyzeComplexity`）。只回答「树结构客观是什么」，不解释实验含义 |
| **Domain Signal / 领域信号**        | 各插件用基础原语自实现、带实验语义的信号检测（如 `detectRollback = detectDiverge(anchor) → satisfaction=0`）。归插件所有，pi-session-tree 不提供                            |

## custom-compaction（压缩实验）

| 术语                                   | 定义                                                                                                                                                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **分层最小写入（Layer-Scoped Write）** | 配置写操作只更新目标层（session/project/user）原始文件中的差异字段，绝不把合并后的全量快照写回单层文件。防止项目级/会话级配置被固化为用户级快照（跨项目污染）。                                                                 |
| **活跃层（Active Scope）**             | 当前生效的配置层（session > project > user；无配置文件时映射为 user）。settings panel 编辑时保存到该层，与面板显示一致。                                                                                                        |
| **回退信号（Rollback Signal）**        | 用户将会话树当前节点回退到压缩摘要节点之前的行为，视为对压缩结果不满意的负信号。pi 无原生事件，靠压缩时记录摘要节点位置、turn_end 对比检测。                                                                                    |
| **重压信号（Recompact Signal）**       | 压缩后用户手动再次 `/custom-compact`，视为对上次压缩不满意的负信号。custom-compaction 内部直接可感知。                                                                                                                          |
| **打标信号（Tag Signal）**             | 用户在会话树节点打 GOOD/BAD 等自然语言标签。pi-lab 默认只解析 `<armId>:<metricId>:<value>` 三字段，自然语言标签需由 custom-compaction 注册自定义 SignalExtractor 做归因翻译。                                                   |
| **归因（Attribution）**                | 把发生在压缩之后的用户行为信号（回退/重压/打标）关联到最近一次压缩所使用的实验臂。pi-lab 设计哲学：armId 归因是消费方 extractor 的职责，pi-lab 只负责存储与统计。                                                               |
| **过程指标（Process Metric）**         | 压缩过程中直接可测的 guardrail 指标：压缩耗时（latency_ms）、token 节省量（saved_tokens）、摘要长度（summary_length）。可作为质量代理，但无法测真实摘要质量。                                                                   |
| **维度实验（Dimension Experiment）**   | 用户要对比的三个独立维度——机制（summarize vs smart-compact adapter）、压缩 prompt 变体、触发阈值。各自注册为独立实验（name 不同），避免臂集混入同一实验。                                                                       |
| **触发条件（Trigger Condition）**      | 每个 profile 各自持有的一份「信号源 + 阈值 + 方向」判定规则，判断该 profile 是否满足触发。**per-profile、多维**：信号源可扩展（context_percent / fixed / reserve / 工具调用次数等），不再只是单一 context 阈值。                |
| **触发粒度（Trigger Granularity）**    | 触发条件评估的频率档位，决定「多久检查一次是否触发」。三档：**user turn**（用户发言提交时）/ **agent turn**（一轮 agent 结束，**默认**）/ **工具处理粒度**（每次工具调用完成）。越细越能及时捕获 context 暴涨，但评估开销越大。 |
| **启用集（Enabled Set）**              | 用户在 settings 面板用 Space 勾选的、参与自动压缩触发评估的 profile 集合。**第一道闸**：列表只是展示，未启用的 profile（含实验项）完全不参与评估；只有被启用的 profile 才会评估其触发条件。                                     |
| **选择算法（Selection Algorithm）**    | 从**触发集**中择一的判定逻辑。形态为**有序路由规则 + 阈值 tiebreak + 兜底默认**（非排序字段）：先按有序路由规则匹配环境，命中后候选仍 >1 时按触发阈值排序取一，无规则命中走兜底。                                               |
| **触发集（Triggered Set）**            | 启用集内满足各自触发条件的 profile 子集，是选择算法的候选范围（= 启用集 ∩ 触发）。**第二道闸**：未满足触发条件的 profile 即使启用，也不进入选择。                                                                               |
| **路由规则（Routing Rule）**           | 选择算法的第一层：形如「当 [环境条件] 满足 → 指定 profile」，规则有序、首条命中生效。环境条件维度目前为：模型（matchModel 降级为其中一条「模型→profile」规则）、复杂度等级（level 三档）。                                      |

### custom-compaction 实验决策（2026-08 确认）

| 决策点               | 结论                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **实验并行性**       | 三个维度实验（机制 / prompt / 阈值）**并行**注册运行。用 pi-lab `select()`/`record()` 直报：每次压缩对各实验独立 `select` 选臂，反馈信号对各实验独立 `record`（armId 即当时 select 结果，存于「最近压缩记录」），消除并行归因混淆。机制实验需 smart_compact adapter 声明 `handlesCompaction: true` 才注册（当前 collaboration 模式无真实机制差异，跳过）。未激活实验的维度（mechanism/prompt 为 null）不覆盖 profile 原配置。 |
| **反馈信号优先级**   | **回退信号最有用**（用户不满时通常回退输入其他 prompt 而非重新压缩）。重压信号保留为补充。打标信号（GOOD/BAD）入口由 pi-session-tree 提供，custom-compaction 只消费。                                                                                                                                                                                                                                                         |
| **实验定位**         | 实事求是收集真实数据（stable-hash 稳定分配），不做 forceArm 固定臂、不讲究初期数据好看。分析时能解释原因即可。                                                                                                                                                                                                                                                                                                                |
| **实验状态展示**     | settings panel 显示实验状态（活跃实验、当前臂、样本量）。                                                                                                                                                                                                                                                                                                                                                                     |
| **自动打标 UI 提醒** | pi-session-tree 自动打标（如不满话语正则规则命中）时，`setStatus` 提示「pi-session-tree 根据 [规则] 打标 [标签]」。tag-engine 已支持 `on:user_message` + `contentPattern`，缺的只是提醒。                                                                                                                                                                                                                                     |

## pi-worktree 隔离开发

> **插件级设计原则：本地优先（见术语 `Local-First` 与 ADR-0061）**——所有操作以**本地 git 状态**为唯一事实来源：基点分支一律解析为**本地 ref**，**绝不隐式 `fetch`、绝不隐式改用 `origin/<b>`**。既有的 `Local-First` / `Local Merge`（2026-08）已确立「不 push、merge 不自动 pull」，但**基点解析**当时未覆盖：`create` 硬编码 `origin/<default>`、`rebase` 在远端存在时 `fetch` + `origin/<b>`——ADR-0061 把这一块补齐；远端状态（ahead/behind）只作**只读提示与建议**，拉取必须由用户显式发起（显式写 `origin/<b>` 或 `--fetch`）。

| 术语                                                 | 定义                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Worktree / 工作区**                                | git worktree 创建的独立工作目录：共享同一仓库历史与远端，各自持有独立分支与文件状态（git 原生概念）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Main Checkout / 主仓库**                           | 仓库的主工作树（默认 clone 目录），不归属任何 worktree。插件以 `ctx.cwd` 是否在受管 worktree 目录下区分身份                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Managed Worktree / 受管工作区**                    | 位于 `<repo>-worktrees/<name>/`（仓库外）且由 pi-worktree 插件管理的工作区；名称来自黄道恒星名池（如 `Aries-Hamal`），分支 `wt/<name>`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Worktree 组 / Worktree Group**                     | 一份**显式声明的固定 worktree 花名册**：成员名列表 + 组基点分支 + 合并策略。批量创建、批量合并、批量回同步均以组为单位，成员不靠销毁重建而靠对齐基点复用（2026-09 确认，取代「从 git 现状隐式推导成员」的 `--all` 默认）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **组目标分支 / Group Base Ref**                      | 组声明中的 `baseRef`：成员分支派生自它、批量合并回落在它（**本项目实例值为 `dev`；代码中不得写死任何分支名**）；成员分支名固定为 `wt/<name>`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **组声明存储 / Group Store**                         | 组声明通过 pi-config 双层存储：用户级 `~/.pi/agent/extensions-data/pi-worktree/config.json` 与仓库级 `<repoRoot>/.pi/extensions-data/pi-worktree/config.json`（**锚定主仓库根，非会话 cwd**），项目级覆盖用户级（2026-09 确认）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **组批量合并 / Group Batch Merge**                   | 按**花名册声明顺序**逐个成员执行「先 rebase 到组目标分支 → 再 squash 合入目标分支 → 提交」；N 个成员 = 目标分支 N 个提交，对齐「1 特性 = 1 提交」。冲突落在 rebase 阶段（有 `continue`/`abort` 支撑），不在 squash 阶段（2026-09 确认，取代「先把成员集成后再一次合入」）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **组失败模型 / Group Failure Model**                 | 批量合并**遇错即停（fail-fast）+ 可续跑**：目标分支保留已完成的 1..i-1 个提交，失败成员停在 rebase 冲突态，解决后 `continue` 自动续跑剩余成员（再遇冲突才停）。**禁止「跳过失败成员继续合并」**——会合入引用不存在代码的假成功提交且 git 不报错（2026-09 确认）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **组合并确认面板 / Group Merge Confirm Panel**       | 执行批量合并前必须弹出的确认列表：内容为「**花名册成员 ∩ 当前实际存在的分支**」，**多选、默认全选**，用户确认后执行（2026-09 用户指定；花名册 ≠ 当前存在，未创建/已删除的成员不出现）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **脏成员展示与禁选 / Dirty Member Shown-But-Locked** | 成员工作区有未提交改动时，**必须出现在 TUI 列表里**（让人看见「这个还没提交」）但**不允许选中**参与后续操作（`dirty(N) 不可选`）；执行层同样硬拒绝，面板不是唯一入口（2026-09 用户指定）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **目标检出状态守卫 / Target Checkout Guard**         | 批量合并前**组目标分支（`baseRef`）所在检出不得处于 merge 进行中**，否则硬拒绝。主检出的**未提交改动不作拒绝理由**——`execMerge` 内部 `stash push` → 合并 → `stash pop`，实测已暂存的在途改动不会被卷进 squash 提交（早期曾据「`merge --squash` 会卷进暂存内容」的错误实测结论硬拒已暂存改动，后经回归用例证伪并撤回）；未暂存的脏文件**不**阻止合并（git 自行拒绝与被合入路径重叠者），不额外守卫                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **批量范围选定 / Batch Scope Selection**             | 批量操作前**一次选定目标范围**（多选、默认全选全部可选成员）——**该批选中成员在后续所有步骤共用同一策略**（不逐个询问、不产生成员间策略分歧）。**候选 = 本次动作真正作用到的对象集合**：组创建 = 尚无 worktree 的成员（已存在的灰显 `exists`）；组合并 = 花名册 ∩ 现有分支中可合入的（脏/无提交者灰显不可选）。**不适用的成员保留在列表里作为上下文**，不做静默过滤（2026-09 用户指定 + 澄清）                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **环境复用策略 / Env Reuse Strategy**                | 组声明中的 `env` 块：为组内**所有成员一次性**设定创建时的环境复用方式，**默认 `copy`（`cp -al` 硬链接）**——共享 inode 省盘，且本地包（`file:` 依赖）解析到**本 worktree 源码**；`symlink` 仍可选，但对 `file:` 本地依赖**必须给出「解析到主仓库源码」警告**（2026-09 确认）。策略选择处**必须展示各策略的空间占用与使用优劣**（用户指定）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **组收尾对齐 / Group Final Alignment**               | 两阶段：① **逐成员即时对齐（必需、自动）**——成员合入成功后立即在其 worktree 内 `reset --hard <当时的组目标分支>`（防下轮「假冲突」：实测未对齐时 rebase 重放已 squash 的内容会冲突）；当前会话 cwd 所在的成员跳过该步。② **统一对齐（问一次、可选）**——整批完成后**再征求一次**是否把所有成员统一对齐到**最终的目标分支**，因为逐成员对齐得到的基线版本各不相同。reset 前把成员旧 tip SHA 写进结果与日志，且**只列本轮已合入成员**（未合入/脏成员灰显不可选）（2026-09 用户指定）                                                                                                                                                                                                                                                                                                                                         |

| **组声明文件 / Group Declaration File**              | schema：`{ "groups": { "<组名>": { "baseRef": "<分支>", "members": ["..."], "mergeStrategy": "squash", "env": { "nodeModules": "copy", "symlinkTargetIds": [...] } } }, "lastNodeModulesStrategy": ..., "lastSymlinkTargetIds": [...] }`（前两项为既有偏好，保持扁平向后兼容）。**层级约束：`groups` 只在仓库级有效**；用户级出现 `groups` 时校验 **warn 并忽略**（绝不静默生效）——组内每项都是仓库事实（成员名、`baseRef`、`symlinkTargetIds` 绑目录结构），脱离仓库无意义；跨仓库复用花名册属于「模板库」新功能，留给将来显式「导入」而非隐式过滤（2026-09 用户确认 A）。两条强制语义：① **写入必须分节读改写**——`save()` 是整体写入该级文件，若直接写入合并结果，会把**仓库级组泄漏进用户级**（反之亦然）；② **数组是替换语义**（`deepMerge` 不追加），故 `members` 不能跨级追加，仓库级要覆盖须写全量（2026-09 确认） |

### pi-worktree 职责边界（2026-08-17 确认）

pi-worktree 是**本地 git 工作区生命周期管理**工具。**不做远端操作。**

| 操作域              | 归属     | 说明                                                                                                                 |
| ------------------- | -------- | -------------------------------------------------------------------------------------------------------------------- |
| 创建/删除/列表/切换 | 插件     | `create`/`delete`/`list`/`use`/`shell` 等本地工作区管理                                                              |
| 同步与合并          | 插件     | `sync`(=rebase 别名)/`rebase`/`rebase-ff`/`merge`/`squash`/`continue`/`abort`/`clean`/`prune`——均为本地 git 仓库操作 |
| 会话管理            | 插件     | `ctx.switchSession()` 切换 cwd 与会话历史                                                                            |
| **push / 远端发布** | **用户** | 合并成功后插件只提示，不执行 `git push`（认证/权限/远端策略属用户决策域）                                            |

**决策归属**：远端发布（push、PR 创建、远程分支管理）由用户自己完成。插件不自动推、不强推，不在命令中隐含远端副作用。

## bash 工具干预

Pi 有两条路径干预内置 bash 工具，单个扩展须二选一。两条路径可共存（tool_call 钩子注入不与 sandbox 的 operations 替换冲突）；真正互斥的是同用 operations 替换的多个扩展之间：

| 术语                                        | 定义                                                                                                                                         |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tool Call Hook / tool_call 钩子注入**     | 在 `tool_call` 事件里 mutate `input`（改 `command`、注入 `timeout`）而不替换工具。与 sandbox 的 operations 替换共存。uv、bash-timeout 采用。 |
| **Operations 替换**                         | 用 `createBashTool()` 的 `operations` 参数整体接管 bash 执行（exec/spawn）。sandbox 采用，属"重"路径，会与其他扩展冲突。                     |
| **默认超时兜底 / Default Timeout Fallback** | bash-timeout 的语义：仅当 agent 未显式指定 `timeout` 时注入默认值（**兜底**），而非**封顶**（上限）；agent 显式传值一律尊重。                |

## permission-gate 权限门禁

| 术语                                                     | 定义                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **危险分级（Danger Tiering）**                           | 按四个正交语义轴（第④轴见「路径出处」）对命中黑名单的操作分级，决定它能否被"动态频次自适应放行"自动放行：①副作用（读 vs 写）②权限相关（是否触碰权限变更）③路径空间（目标路径是否落在敏感/核心区域）。产生副作用的操作至少 info 级以上；副作用+权限相关、或路径落在 Linux 核心区域 → critical。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **副作用（side effect）**                                | 操作对系统产生变更（写/删除/修改），区别于纯读。是分级的第一判据：有副作用至少 info 级以上，无副作用（纯读）为最低档。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **权限相关（permission-related）**                       | 操作涉及权限/身份变更（chmod/chown/sudo/su/setfacl/usermod/mount 等）。副作用+权限相关 → critical；`sudo` 一律 critical，不解析其后续命令（提权即最高警戒）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **危险命令（destructive command）**                      | 本身具破坏性/影响系统运行的命令（dd/mkfs/fdisk/parted/wipefs/shred/iptables/nftables/shutdown/reboot 等）。命令字面匹配 → 一律 critical。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **路径空间（path surface）**                             | 操作目标路径所在区域，分两层判定：①**系统目录层**（/etc /usr /boot /lib /sbin /bin /sys /proc /dev）——写 = critical、读 = warning；②**敏感凭证层**（~/.ssh ~/.aws ~/.kube ~/.gnupg、项目内 `.env` `*.pem` `*.key` `id_rsa`）——读 = 写 = critical（读凭证即信息泄露）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **项目身份（project key）**                              | 审计归档与历史/策略过滤用的**仓库级**标识：`git remote get-url origin` 的 SHA256 前 12 位（`git:…`）；无 remote 时退回目录路径 hash（`path:…`）。**同一仓库的所有 worktree 共享同一个项目身份**。注意它与「信任范围」刻意不同（同一份代码里两套身份并存）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **信任范围（trust scope）**                              | 动态频次自适应放行**生效的目录边界**（配置项 `dynamicPolicy.scope`，一条**根列表**，每根可挂条件）：cwd 与命令的每个目标路径都必须落在其中，计数才可用于自动放行。与「项目身份」刻意不同——信任**不因「同一个仓库」自动扩散**到别的 worktree。⚠ 与「放行规则持久化层级」的 session/project/user 是两回事，勿混用 `scope` 一词。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **路径出处（path provenance）**                          | 判定模型的**第四轴**（与副作用 / 权限相关 / 路径空间正交）：目标路径是否由**本会话**（同一 sessionId）的命令创建过。语义依据：**删除本会话已获批创建的路径 ⊆ 已授权集合**（创建动作本身已过闸）；跨会话不成立（可能是别的会话/agent 放的），故会话边界既是够用的、也是原则性的。判定以静态账本为主（解析 mkdir/mktemp/touch/git clone/tee/重定向 + 命令内变量绑定），目标 mtime 兜底**仅限 临时区根**；账本在 session_start 时从审计日志按 sessionId 重建，不新增持久化。解析阶梯由强到弱：①命令内字面路径片段 ②命令内变量绑定（含 `$(mktemp -d)`——模板 `${TMPDIR:-/tmp}/tmp.XXXXXXXXXX` 静态可判）③会话级变量账本（跨命令绑定）④不可判则退回位置类别，不猜。**范围扩面后本轴是唯一护栏**——把 `/tmp` 之类纳入信任范围时必须同时挂「仅限本会话创建的路径」，否则现成的工具级规则会放行任意目标（因 `checkThreshold` 是 OR 语义，见 ADR-0059）。 |
| **并行毕业（parallel graduation）**                      | 动态频次自适应放行的三个计数维度（命令 2 次 / 工具 3 次 / 目标目录 4 次）**各自独立**，任一达标即放行（`checkThreshold` 的 `const pass = passing.length > 0`）。后果：`tool:rm ≥ 3` 等价于「信任范围内**任意目标的** `rm`」。这是「目标常变记不住」对本插件**不成立**的根因（见 ADR-0060 收缩节）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **提升候选键（promotion candidate key）**                | 提升/计数候选的锚点**不由算法预设**，而是**由用户在确认卡片上从叶子向上选定的层级**（①具体路径 ← 默认 ②父目录 ③已知临时区根——台阶顶层是「**目标根**」，不是「路径类别」，**不需要分类学**；认不出的路径**不提供**③级）。阶台不是纯词法爬升（6 个 worktree 在 `.pi/tmp` 之上无有意义的共同祖先），故需要命名的停靠站（`<项目>/.pi/tmp`、`/tmp`）。理由：变量间接目标占 rm 的 54%，现有 `dir:` 轴（锚在父目录）对其失效；实测能归类的目标 100% 落在 `/tmp` 或项目内 `.pi/tmp`——**变的是值，稳定的是来源**。命令名不参与泛化（不做「命令形状」档）。泛化必须配路径出处约束（见 ADR-0060）。                                                                                                                                                                                                                                                       |
| **临时区（scratch）**                                    | 位置类别中「局部可逆、非敏感、非共享权威」的写入区（如 `/tmp`、`$TMPDIR`、`~/.cache`、项目内 `.pi/tmp` 与构建产物目录）。落在此类目标下的写/删按 warning 分级；也是路径出处兜底判定（mtime）的**唯一作用域**——项目正文目录不适用 mtime 兜底，避免吞掉用户刚创建的内容。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **失败即拒绝（fail-closed）**                            | 不可判定（解析失败/异常/无法确认意图）时，默认拒绝或询问，而非放行。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **动态频次自适应放行（graduated auto-approval）**        | 同一命令/工具/文件夹达到确认次数阈值后，后续同类操作自动放行的机制。放行规则的持久化层级受危险等级限制（见下）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **放行规则持久化层级（approval-rule persistence tier）** | 自适应放行规则可沉淀的最高层级，由危险等级决定：critical → 会话级（会话结束失效）；warning → 项目级；info → 用户级。危险等级越高，信任越不持久。该映射关系展示在策略面板底部提示。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **提升建议（promotion suggestion）**                     | 插件从真实历史（审计 + 三层策略）归纳出的候选：建议把某条放行原则的作用范围从「当前项目」扩大到「用户级 / 多个项目」。**不自动生效**——permission-gate 面板首个 tab 展示候选与证据明细，人类逐条确认后才落盘。区别于 graduated 自动沉淀（无人工确认）与手动策略（当场拍板），也区别于 preset 的「提升」（人工按键转移、无候选发现）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **手动创建策略（manual rule creation）**                 | 用户在阻断确认框中对某条子命令按 `a` 显式「添加为策略」，跳过算法计数累积，直接创建一条放行规则（一步流程：`a` → 级别选择 → 创建）。匹配粒度默认精确命令级，工具/目录扩展在策略面板操作。与算法沉淀（graduated）相互独立，两套机制并存，判定时手动策略优先。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **手动策略（manual strategy）**                          | 手动创建策略产生的显式规则，独立存储（区别于 graduated 的计数）。用户拍板的信任：不受阈值调整影响、面板行标记 `手动`（graduated 行 `自动`，不带方括号）、删除/调级独立操作。会话结束时其会话级条目随会话清除。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **默认沉淀级别（default persistence scope）**            | 手动创建策略时的初始持久化层级，默认会话级（会话结束失效），用户可在设置中修改。仅作为手动创建策略的默认选项；算法沉淀仍按 tier→scope 映射（critical→会话 / warning→项目 / info→用户）自动决定层级。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **动态频次自适应放行默认开启（graduated default-on）**   | `dynamicPolicyEnabled` 默认 true——同一命令确认达阈值后自动放行（无感），解决"反复确认同一命令"痛点。graduated 仍按 tier→scope 映射决定持久化层级；手动策略（用户拍板）与其并存。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **阻断确认树（blocking confirmation tree）**             | 危险命令拦截窗口的展示形态：命令树（根 = 完整命令，叶子 = 拆解的子命令，两层树，可折叠），节点前用不同颜色小点提示风险（参考 custom-tree 样式）。仅作展示与细粒度管理入口，不影响放行语义。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **整命令放行语义（whole-command approval semantics）**   | 拦截窗口的放行/拒绝作用于整条命令：放行 = 原命令不改写直接执行；拒绝 = 整条不执行。不做部分执行/命令改写（改写后 LLM 原本想做的操作已变，无意义）。放行决策是会话级语义。叶子级「添加为策略/加入拦截规则」是粒度更细的管理操作，与本次放行决策相互独立。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **请求/控制 ID（request/control ID）**                   | 每次命令执行（工具调用）生成的唯一标识，贯穿审计回溯与外部确认：被拦截（ask）的记录其 ID 供外部通道凭 ID 确认；放行的记录其 ID 仅用于审计。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **外部确认通道（external confirmation channel）**        | permission-gate 暴露的通道无关程序化确认接口（`globalThis.__permissionGateApi`：`onPendingRequest` + `confirm` + `listPending`）。任何插件（如 wechatbot）可订阅待确认请求并程序化确认，等效于人工 TUI 选择。permission-gate 阻塞行为不因外部通道而变，超时/作废由通道自身控制。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **审计日志（audit log）**                                | 每次命令执行（全部工具调用）的完整记录（ID、时间、工具、命令、级别、决策、命中维度），JSONL 按天分片存储，默认保留半年、滚动清理。是审计回溯与"回检拦截强度"的数据源，也是未来智能自适应算法的语料。放行规则与配置**永久保留**，不受半年限制。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

## preset 预设

| 术语                                         | 定义                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **preset 三级来源（preset scope）**          | preset 定义的三个作用域：会话级（TUI 会话内临时添加，仅存内存，会话结束失效）、项目级（项目本地配置文件）、全局级（用户级配置文件，跨项目）。面板每行头部以 `[会话]` `[项目]` `[全局]` 标记来源。                                                                                                                                                    |
| **会话级 preset（session-scope preset）**    | 仅在当前会话内存中存在的 preset，只能通过 TUI 面板添加，不做文件持久化，会话结束失效。                                                                                                                                                                                                                                                               |
| **项目级 preset（project-scope preset）**    | 定义在 `<cwd>/.pi/extensions-data/preset/config.json`，仅当前项目可见，只能通过配置文件修改。                                                                                                                                                                                                                                                        |
| **全局级 preset（global-scope preset）**     | 定义在 `~/.pi/agent/extensions-data/preset/config.json`，跨项目可见，只能通过配置文件修改。                                                                                                                                                                                                                                                          |
| **提升（promote）**                          | 会话级 preset 调好后，通过 TUI 的 `s` 键写入项目级 config.json 并移除会话级同名条目，实现「临时试验 → 项目固化」的转正。全局级不提供 TUI 提升入口，用户自行拷贝项目级配置文件到用户级。                                                                                                                                                              |
| **复制为临时（copy-to-session）**            | 文件级 preset（项目/全局）在面板按 `e` 复制为会话级副本，命名 `原名-复制`（重名递增 `-复制2`），副本完整继承原字段并可继续编辑，原文件级不变。                                                                                                                                                                                                       |
| **preset 策略源（preset as policy source）** | preset 是 tools / skills / instructions 三个维度的**唯一策略声明者**；`/tools`、`/skills`、`/prompt` 是它在各维度上的执行臂（子工具），不得形成与 preset 冲突的策略。定位为**硬约束**：激活时按 preset 设定强制生效，而非仅提示偏离。tools 白名单为**封闭集**——激活期间运行时新注册的工具（org/MCP 等）一律视为禁用，`/tools` 视图同样显示为不可用。 |
| **子工具（sub-tool）**                       | preset 的三个维度执行臂——`/tools`（活动工具集）、`/skills`（技能可见集）、`/prompt`（指令注入）。三者与 preset 的控制状态必须时刻一致（例外见下条「已知例外」）。                                                                                                                                                                                    |
| **已知例外（known exception）**              | 由 pi 运行时机理决定、不要求 preset/子工具做到完全一致的两点（ADR-0049「已知例外与限制」）：① skills 控制不保证与用户经 `/skill:xxx` 实际可达的技能一致；② 动态工具遮罩对当轮 system prompt 可能滞后一轮（工具调用层不滞后）。                                                                                                                       |
| **无 preset 状态（none）**                   | 未激活任何 preset 的状态。此时 preset 不施加任何限制（各子工具回到"无策略"的默认行为）。_避免_ 与 preset 的 `tools: []` 字段（某维度不限制）混淆——后者是"有 preset，但该维度不限"。                                                                                                                                                                  |
| **基础层（base layer）**                     | preset **未激活**时三个子工具各自维护的状态（默认：工具全量启用 / 技能全部可见 / 无附加指令）。用户在此层的手动偏好（如 `/tools` 关掉某工具）是基础层状态，清除 preset 后保留。                                                                                                                                                                      |
| **约束叠加层（policy overlay）**             | preset **激活期间**叠加在基础层之上的硬约束。清除 preset = 仅撤回 overlay，基础层原样保留；preset 的任何路径都不得把约束写进基础层。                                                                                                                                                                                                                 |
| **活动工具集（active tool set）**            | pi 运行时实际可被 agent 调用的工具集合（`pi.getActiveTools()` / `setActiveTools()`）。`/tools` 面板视图与 preset 的 tools 策略共同指向它，是工具维度的单一事实源。                                                                                                                                                                                   |

## 本地同步（sync 工具）

| 术语                                | 定义                                                                                                                                                                                                                                                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **同步 profile（sync profile）**    | `scripts/sync-profiles.yaml` 中定义的一组「资源清单 + 目标目录」，描述把哪些 assets 同步到哪里（如 `user-install` → `~/.pi/agent`、`project` → `./.pi`）。_避免_ 与 review profile / custom-compaction profile 混淆（三者是不同域的同名概念）。                      |
| **受管资产（Managed Asset）**       | 目标目录中、名字能在本仓库源清单（`extensions/`、`skills/`、`themes/`、`prompts/`）按名匹配到的资产。sync 默认删除谓词的作用对象。_避免_：自有资产、仓库资产。                                                                                                       |
| **第三方资产（Third-party Asset）** | 目标目录中名字不在源清单里的资产（如 herdr 安装的集成）。sync 默认永不删除，仅 `--purge` 才清。                                                                                                                                                                      |
| **有效集合（Effective Set）**       | 一个 profile 实际要同步的资产名集合 = include（`*` 或显式清单）减去 exclude。删除判定用「不在有效集合」而非「不在 include」。                                                                                                                                        |
| **严格剪枝（Strict Prune）**        | sync 默认删除谓词：受管资产 且 不在当前 profile 有效集合 且 不在保护名单 → 删除。区别于 `--purge`（连第三方也删）。                                                                                                                                                  |
| **形态冲突（Form Conflict）**       | 目标里名字 ∈ 源清单、但形态与源不一致的残留（源是目录扩展、目标残留同名单文件 `.ts`，或反向）。也按受管资产删除，且不受 purge/inline 决策影响。典型：`review` 重构为目录后残留旧 `review.ts` → pi 加载两次 → `review:1`/`review:2` 重名。                            |
| **保护名单（Protected External）**  | `PROTECTED_EXTERNAL`，第三方集成名清单（如 `herdr-agent-state`），删除判定时跳过，避免误删用户手动安装的集成。                                                                                                                                                       |
| **墓碑清单（Retired List）**        | `sync-profiles.yaml` 顶层 `retired` 字段，登记本仓库曾管理、现已下架/内嵌（名字从源清单消失）的扩展名。sync 构建源清单时把它们并入，使目标残留的同名旧副本被当作受管资产删除，而非误判为第三方永久保留（否则与内嵌后重新注册的同名扩展重名 → `tools:1`/`tools:2`）。 |

## 多 agent 框架（目录绑定 agent）

| 术语                                        | 定义                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目录绑定 agent（directory-bound agent）** | 一个目录 = 一个 agent 的**存在边界**：目录内 manifest + `AGENTS.md` 赋予其身份/角色/能力/工具/知识，并承载记忆与资产、作为沙箱作用域锚点。_避免_：子 agent、子会话（父子从属模型，非对等实体）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **org（协作组织）**                         | 具名、可创建多个的 agent 协作组织：数据按 `~/.pi/org/<org名>/` 独立存放（成员花名册 / 任务记录 / 待办对应表 / 运行时），每个 org 有且只有一个负责人。_避免_：公司、团队、全局单例组织。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **负责人 agent**                            | org 的唯一通才（单一角色）：维护注意力清单 + 拆解任务 + 派发 + 验收 + 汇总 + 与人类用户沟通。负责人派发的任务**单方生效**（无需他人确认）；非负责人派发需握手确认（见「握手」）。_避免_：总决策 agent、决策通才、Chief of Staff。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **子领域 agent**                            | org 成员，各管一个领域、一个目录，独立 pi 进程、独立上下文/记忆/资产/沙箱，非常驻、按需唤醒。一目录 = 一员工（一人格），可同时加入多个 org。_避免_：员工、分工 agent、领域 agent。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **agent 注册表**                            | 全局 `~/.pi/org/` 下登记的静态清单：哪些目录是子领域 agent + 其 manifest 元数据，回答「有哪些员工可唤醒」。_避免_：花名册、registry、注册表。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **握手（handshake）**                       | 非负责人 agent 派发任务的确认机制：派发方发起 + 被派方确认，双方都同意才形成任务记录。负责人派发不经握手直接生效。规则细节见 ADR-0038。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **在岗 / 存活 / 忙碌**                      | 组织感知三态：**在岗**（旧称"存活"）= 该成员目录下的 pi 进程，其 control 控制 socket **真的可连**——可被 org 感知、可收发成员间消息；**同目录未在岗的普通 pi 不算在岗**（不写 runtime、不感知 org 能力）。在岗与否只门控**进程级交互**（收发成员间消息、即时投递）；**目录级组织数据**（成员表、任务、设置）的增删改不受门控。忙碌 = 正在处理任务（turn 中）；资源占用 = pid 的 CPU/内存（2026-09 定）。**判据来源（2026-09-11，ADR-0043 `D2`，已落地）**：以「runtime 记录存在且其 `socketPath` 可连」为准——flag / argv 只表示"启动时请求建 socket"，`getFlag` 按扩展隔离（对本扩展恒 `undefined`），故不作判据；会话内**上岗/离岗由 org 自决**：`/org on`（ADR-0046），`/control on/off` 只管 socket（必要条件，不驱动 org）。 |
| **在岗简报**                                | 在岗成员进程的知识块——①**定位**（org/角色/简介）；②**在岗成员**（名字+状态）；③**组织背景**（`org.json` 的 `background`）；④**最近动态**（未结任务、未读 inbox）；⑤**可用技能**（技能名+时机，正文按需 `read`）。**静态**（①③⑤）由 `before_agent_start` 恒定进**系统提示**；**动态**（②④）经 `input` transform 追在每个**用户轮次尾部**（随用户消息持久化，**每轮都追加**，不含简介）——不写"每轮变化的系统提示"，避免 prompt cache 全量失效。仅**在岗**进程获得。_避免_：组织上下文、org 上下文块、知识块、prompt 注入。                                                                                                                                                                                                        |
| **成员简介**                                | 成员对自身职责的一句话描述，存于其目录 `pi.agent.json` 的 `description`（`org.json` 的 `member.manifest` 里存的是**快照**，故需刷新规则：①**在岗注册**时成员回写自己的；②看板 `r` 刷新时重读全体成员目录；③渲染**在岗简报**时实时重读。③只读不回写——每轮回写会带来每轮写盘与多成员并发**丢更新**。_避免_：profile、个人简介。                                                                                                                                                                                                                                                                                                                                                                                                   |
| **对等编排（peer orchestration）**          | 目录 agent 之间经 socket 做双向/单向对话的编排关系，非父子从属。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **dispatch_task（派发工具）**               | 任意 agent 派发任务的结构化工具：LLM 自主决策 + 落任务账本 + 携带任务上下文。负责人派发单方生效；其他 agent 派发走握手确认。_避免_：裸 `send_to_session`。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **任务上下文**                              | `dispatch_task` 附带的结构化材料（任务描述 + 材料 + 前置讨论摘要 + 约束 + 验收标准 + 引用来源），格式参考 handoff 技能。_避免_：上下文包。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **注意力清单**                              | 负责人 agent 维护的「人 + 团队」双来源注意力视图：观察人类用户行为 + 子领域 agent 任务状态/阻塞，生成「现在关注什么、下一步谁上」。_避免_：优先级清单、todo 清单。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **mission / receipt / lane evidence**       | 可指认性三件套（模块级移植自 nicobailon）：mission = 任务账本（谁/什么任务/状态）；receipt = 交付回执（结果证据链接）；lane evidence = 合并/审核证据（谁 merge、谁 attest）。回答「哪个 agent 在哪个分工没做好」。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **例程（routine）**                         | 「谁来做 + 什么时候做」的定时例行任务原语。_TODO_：定时触发等 cron 插件，本框架只预留例程定义数据结构。_避免_：skill（skill=怎么做，routine=谁+何时做）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **错误学习闭环**                            | agent 犯错 → 自动记录（mission/receipt）→ LLM 根因分析 → 人审核更新 playbook。_TODO_：作为独立 meta 插件，本框架预留接口。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **死机判定 / 健康检查**                     | 插件提供健康检查 + 死机判定标准报告；杀进程仅人类用户下指令调用 skill 才执行（agent 不主动发起 kill）。 **补充（2026-09-10）**：负责人 agent 可发起「主动唤醒」（spawn 成员进程）；**杀停（kill）仍限人类下指令**——唤醒与杀停不对称授权。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **任务记录（org 层官方任务）**              | org 共享、大家可见的任务账本条目（`~/.pi/org/<org名>/tasks/`）：任务编号 / 标题 / 概要背景 / 逐点任务清单 / 派发人 / 期望完成时间（可空）/ 子任务数组 / 验收记录。_避免_：mission（旧称，见下方三件套条目）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **子任务**                                  | 一个任务拆给每个处理人的那一份工作：每个处理人一个子任务，各自有状态与交付记录；一个任务的全部子任务交付齐后通知派发人可验收。_避免_：里程碑。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **派发人**                                  | 发起并负责一个任务的 agent（通常是负责人，但不限于）：只有派发人能验收与关闭该任务。_避免_：sender、发起者。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **处理人**                                  | 被派发并实际执行某个子任务的 agent。_避免_：assignee、受派者、执行者。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **期望完成时间**                            | 任务记录上的可选时间字段（可为空）：派发人给出，用于排期与超时提醒。_避免_：due、DDL。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **交付（delivery）**                        | 处理人把完成结果（结果摘要 + 产出文件，产出可指到具体行）交回的动作与记录。员工在自己工作台把待办标「已完成」即交付声明，驱动交付内容回传。_避免_：submit、提交（与 git 混淆）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **验收**                                    | 派发人对已交付的子任务/任务给出「通过 / 打回」结论的动作；agent 路径（命令/工具）只有派发人能验收并关闭任务。时机与粒度由派发人自主决定。人经 TUI 可强制验收/打回/关闭（见「人类强制」）。_避免_：submit、approve（英文）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **两级通知**                                | 系统如实通知派发人：某个子任务交付了（一次）；全部子任务都交付了（再一次）。只陈述事实，验收决策留给派发人。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **员工工作台（个人待办）**                  | agent 自己维护的待办清单，落员工目录 `.pi/todos/`（todos 插件同源文件格式），可混入个人事项；员工标「已完成」= 交付声明。_避免_：个人 todo（英文混写）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **对账**                                    | 把官方任务记录与员工工作台待办两边核对的机制：待办标完成但缺交付 → 提醒补交付；官方已验收关闭但待办未归档 → 提示归档；只提醒、不静默改任一边。_避免_：reconcile、同步（含义太宽）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **紧急 / 重要 标签**                        | 待办条目 tags 上的约定标签（urgent / important），用于表达优先级；不引入数值优先级字段，排序判断留给 agent。_避免_：P0/P1 数值。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **可感知状态（perceivable state）**         | 组织视角下某成员「能否被感知/触达」的展示四态（圆点映射见 ADR-0040 D5）：**睡眠** = 进程不在（无 runtime 或 socket 不可连；socket 不可连但进程存活时仍按"不可达"展示，但**不清理其 runtime、不重复拉起**）；**空闲** = 在岗且 `busy=false` 且名下无待验收交付；**工作中** = 在岗且 `busy=true`；**完成工作待验收** = 在岗、`busy=false` 且名下有 `delivered` 参与者项。派生自既有的「存活 + 忙碌」两轴 + 任务参与者态（见上文「在岗 / 存活 / 忙碌」），**非新造指标**。_避免_：在线/离线/上线/下线（易与 socket 混淆）。                                                                                                                                                                                                        |
| **org 能力作用域**                          | org 能力（技能 / 工具 / 上下文感知）与动作的适用面——**在岗** = 进程级可达（可收发成员间消息）；**纯数据动作**（踢退 / 设负责人 / 改名 / autoWake / 派活落 inbox 兜底）不要求在岗；**需进程配合的交互**（实时收发消息、即时投递）仅限在岗（2026-09 定）。**门控只及 LLM 可见面**（工具 / 技能 / 在岗简报）；**人类操作台**（`/org` 命令、看板）**永远可用**——否则未在岗的目录会自锁，`/org join`、看板 `w` 唤醒都进不去（2026-09 定）。_避免_：管理范围、权限范围                                                                                                                                                                                                                                                                |
| **主动唤醒（active wake）**                 | 成员处于「睡眠」时，由**人类（TUI 看板）或该 org 负责人 agent**主动在其注册 cwd 启动 `pi -a --session-control`（带该成员的**启动参数**，见下条；并带入上次 sessionId 续接）的动作。_避免_：spawn（实现细节名，领域词用"唤醒"）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **睡眠 / 休眠（stop）**                     | 主动**杀停**某成员的 pi 进程，并持久化其最后 sessionId 供下次唤醒续接。**触发者限人类**（看板 `s` 二次确认）——唤醒与杀停**不对称授权**：唤醒是可恢复的正向动作；杀停会打断他人进程，故**负责人 agent 亦不可发起**（与「唤醒」条不同，见 ADR-0040 `D2`/`D10`）。_避免_：kill（实现细节名）。                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **成员启动参数（launchArgs）**              | 唤醒成员时**追加在固定启动项之后**的参数（固定项 `-a --session-control [--session-id …]` 不可编辑）。**加入组织时**从插件配置取初值写进成员记录（默认 `--no-permission-gate`——成员在 tmux 里无人值守，权限门的确认弹层没人应答会无限挂起），此后**以成员记录为准**；记录无该字段 = 不带任何额外参数（不回填、不兜底）。**只有人类操作台能改**（成员视角隐藏）：看板成员视角 → `p`（编辑时先展示现值；留空保存 = 删除该参数），改后不影响已启动的进程。自动唤醒与人对看板按键的唤醒读同一份配置、行为一致，见 ADR-0051。_避免_：启动命令、命令行。                                                                                                                                                                               |
| **巡检（presence polling）**                | 看板打开期间的**只读**轮询（`setInterval`），仅刷新「可感知状态」；**不产生任何副作用**（不唤醒、不杀停）。关闭看板即停。原则：**感知与动作分离**——感知循环里绝不写副作用。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **可上岗（待上岗）**                        | control socket 可连（必要条件已满足）但本会话尚未 `/org on` 的状态：org 能力（工具 / 技能 / 简报）仍不注册，状态栏提示「待上岗」。_避免_：在线、已连接、准在岗。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **在岗入口**                                | 让「某个已有 pi 进程」成为在岗进程的手段。**唯一入口是 org 自决（ADR-0046 D1，2026-09-12 已落地）**：会话内 `/org on` / `/org off`（命令 + `/org` 看板一级项）。前提是**可上岗**（control socket 可连，必要条件）——`/control on/off` 只管 socket，**不**驱动 org 上岗。启动时若 socket 已可连则自动上岗（保留便利，ADR-0046 D4）。_避免_：在线开关、上线按钮、把 `/control on` 当成上岗。                                                                                                                                                                                                                                                                                                                                       |
| **在岗判据**                                | 判定某成员「在岗」的依据。**必要条件（ADR-0043 D2）**：runtime 记录存在且其 `socketPath` 可连 = 「可收发成员间消息」的物理真相；**flag 只表示启动时请求建 socket，不作判据**。**充分性由 org 自决**（ADR-0046 D2，2026-09-12）：socket 可连 **且** 本会话已 `/org on`，两者同时成立才算在岗。_避免_：以 flag / argv / pid 判在岗、把「可上岗」当成「在岗」。                                                                                                                                                                                                                                                                                                                                                                    |
| **成员消息（member message）**              | 成员间经 control socket 投递、在接收方以 `customType:session-message` 注入的消息；给 LLM 时被压成 `role:user` 原文，**与人类输入同形**（ADR-0043 背景）。_避免_：系统消息、agent 消息。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **发送者头（sender header）**               | 成员消息携带来源的统一头。**已落地（ADR-0044 D2/D3/D4）**：复用 control 的 `<sender_info>{sessionId?,sessionName?}</sender_info>` 机器可解析格式（sender 用 org 成员名），显示层渲染为 `[成员名]:`；系统提示静态块声明「带此头 = 来自成员 agent，非人类操作者」。_避免_：前缀、昵称标记。**注意**：仅是声明，不构成防伪造。                                                                                                                                                                                                                                                                                                                                                                                                     |
| **显式唤醒（explicit wake）**               | 由**该 org 负责人 agent**（工具）或**人类**（命令 / 看板当面操作）发出的「把某睡眠成员叫起来」的动作：幂等、不改组织数据、不产生任务——与「派活」分离（有些场景只需叫醒）。受「自动唤醒开关」门禁（看板当面操作例外，见「唤醒入口」）。_避免_：spawn（实现细节名）、把它当成派活。                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **唤醒入口**                                | 唤醒的**允许路径**，受「自动唤醒开关」门禁（2026-09-13 收紧）：开关**开**时——① **自动**：负责人 agent 派活时若感知目标睡眠，则先唤醒再投递；② **自主 / 命令**：agent 工具与 `/org …` 命令可显式唤醒；开关**关**时——**不存在任何自主或命令唤醒路径**（派活自动、agent 工具、`/org` 命令一律不得唤醒），成员保持下线、任务落 inbox 兜底，agent 应停下来请人处理。**唯一例外**：人类在 TUI 看板对选中成员的**当面操作**（`w` 唤醒 / `s` 睡眠）**不受开关约束**（ADR-0041「人类操作台永远可用」）。_避免_：把唤醒挂到巡检上（违反感知与动作分离）、把「开关关」误读成成员不可被叫醒。                                                                                                                                               |
| **自动唤醒开关（autoWake）**                | 控制「该组织是否允许**自主 / 命令**唤醒睡眠成员」的总门（2026-09-13 收紧语义）。**开**：负责人派活即先唤醒再投递，且允许显式唤醒动作；**关**：**任何自主或命令路径都不得唤醒**，派活只落 inbox 兜底、不强拉进程，agent 遇此情形应停下请人处理。**例外**：人类在看板对选中成员的当面操作不受门禁（见「唤醒入口」）。**只有人类**能改此开关（TUI 设置页 `s` → 设置页）。存储与作用域（2026-09-10 定）：按公司存于 `~/.pi/org/<公司>/org.json` 的 `settings.autoWake`，作用域 = **该组织**（多公司可各自开关）；**不进插件配置**（TUI 界面偏好才是插件配置，见 ADR-0039 §H）。                                                                                                                                                     |
| **任务看板（/org 面板）**                   | 人类管理台 TUI：`/org`（无参数）打开。顶层公司 tab 切换本机全部组织 → 视角层 [任务视角] [成员视角] [设置] → 任务视角下 4 个状态子 tab（待办 / 进行中 / 等待验收 / 已关闭）列表，支持按时间排序与关键字搜索；二级详情含人类操作（验收 / 打回 / 改派 / 取消）。不用泳道卡片。交互与身份语义见 ADR-0039。_避免_：kanban、泳道看板。                                                                                                                                                                                                                                                                                                                                                                                                |
| **人类强制（human@ 操作）**                 | 人经 TUI（人操作台）执行、越过派发人限定的动作（验收 / 打回 / 取消 / 改派）：人位于组织之上，面板可见任务不分 org 不分派发人都可操作，任何僵死任务可经此收尾。落账 `by` = `human@<打开面板目录名>`（不记 agent 名，审计可辨人干预）、history 事件 `human_forced_*`；铁终态对人也生效（关闭不可重开）。agent 的命令面/工具不受影响、仍限派发人。_避免_：admin、管理员操作、sudo。                                                                                                                                                                                                                                                                                                                                                |
| **成员动态（member activity）**             | 人类在 TUI 看板里了解「某成员最近在干什么」的**只读观测**：从**在岗成员进程**经 control 控制 socket 拉取其最近事件（文本汇报 / 工具调用及其 diff 摘要）。**只在看板打开期间拉取**（随「巡检」生命周期，关闭即停，不做后台常驻轮询）；**不参与「可感知状态」判定、不进任务账本、不受唤醒门禁约束**——它回答「在干什么」，不回答「在不在」（四态）。数据源是成员进程内的会话分支，非会话文件、非 LLM 摘要。_避免_：成员状态、在线状态、进度（易与「可感知状态」四态混淆）。                                                                                                                                                                                                                                                        |
| **中断（interrupt）**                       | 人类（看板成员视角按 `x`、`/org abort <成员>`）或**该 org 负责人**（`org_abort` 工具）对在岗成员发出的「停当前这一轮」动作（≈在它终端按 ESC）：**幂等、只停当前轮**，进程 / 会话 / 记忆都保留，不产生任务、不改组织数据。**不受「自动唤醒开关」门禁**（是「停」不是「起」）；据实回报（不在岗 / 进程版本旧都说明原因），**绝不假装成功**。与「睡眠」的区别：睡眠是**进程级**停（杀进程），中断只停一轮。_避免_：暂停、stop、kill、ESC（实现细节名）。                                                                                                                                                                                                                                                                           |
| **重试（retry）**                           | 把**同一个任务**重新投递给**同一个参与者**（`/org retry <任务号> [成员名]`、看板任务详情按 `t`）：附一行「上次中断/失败」说明，走既有投递通道（不在岗落 inbox，任务不丢）。**不改任务编号、不动账本状态**——参与者状态机受保护且没有「回到已派发」的迁移，中断只停当前轮、归属未变。三类情形**不**走重试：已交付 → 走**打回**（轮次 +1）；已叫停/取消 → 走**改派**；任务已 `closed`（铁终态）→ **新开任务并引用**。_避免_：重开、重启、再派（易与新任务混淆）。                                                                                                                                                                                                                                                                  |

## pi-rewind（checkpoint / 回滚）

基于 oh-my-pi 的 `@ayulab/pi-rewind` + `@ayulab/pi-checkpoint`（GPL-3.0）移植，单包 `extensions/auto/pi-rewind/`，引擎内联 `engine/`。ADR-0038（存储与回滚模型）、ADR-0039（架构分层与跨插件边界）。

| 术语                                      | 定义                                                                                                                                                                                           |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Checkpoint / 检查点**                   | 一条用户消息跨度的工作区快照：beforeCommit = 该消息前状态，afterCommit = 整个 loop 结束后状态。存独立 bare repo，元数据以 `pi-checkpoint` custom entry 写入会话树。_避免_：snapshot、savepoint |
| **User Message / 用户消息**               | checkpoint 的跨度单位：一条用户 prompt（可触发多轮 agent turn）。一个用户消息 = 一个 checkpoint。_避免_：prompt、turn                                                                          |
| **Turn / Agent 轮次**                     | 一次 user→agent 响应循环。checkpoint 不按 turn 打（loop 内多轮共享一个 beforeCommit）。_避免_：step、round                                                                                     |
| **beforeCommit / afterCommit**            | 快照的两个 commit 哈希：消息前 / loop 结束后。无文件变更时二者相同（不建空 commit）                                                                                                            |
| **Checkpoint Storage / 检查点存储**       | 每会话一个独立 bare repo（`~/.pi/agent/rewind/checkpoints/<sid>/`），work tree 指向项目目录；不写用户真实 git                                                                                  |
| **触发策略 / Checkpoint Trigger**         | `checkpointTrigger`：`message`（每条用户消息）/ `event`（仅 fork/clone/tree/命令时）/ `off`。`batch`（每 N 条）已挂起                                                                          |
| **恢复触发 / Restore Trigger**            | `restoreOnTree`/`restoreOnFork`/`restoreOnClone` 三态 `never / ask / always`；`restoreOnResume` 布尔                                                                                           |
| **Safe Checkout / 安全检出**              | dirty guard + safety commit + 失败自动 rollback 的回滚原语                                                                                                                                     |
| **跨插件抑制 / Cross-plugin Suppression** | 其他插件经 `globalThis.__piRewind.suppressTreeRestore()` 跳过下一次树导航的文件回滚（review 开审查分支用），`clearSuppressTreeRestore` 在 finally 清除                                         |
| **体积保护 / Size Guard**                 | `maxFileMB` / `skipBinary` / `includeUntracked` 三 knob，stage 时跳过超大/二进制/untracked 文件                                                                                                |
| **保留策略 / Retention**                  | `retentionDays` 按 storage manifest 的 `updatedAt` 清理过期 checkpoint storage；`/checkpoint` 手动删除 UI 并存                                                                                 |

## pi 版本基座（升级与兼容）

| 术语                             | 定义                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **基座（base）**                 | "我们在哪个 pi 版本上做过适配"的统称，**永远指类型基座与运行基座的一致性**，不指其中之一。见 ADR-0063。_避免_：版本、踩点（无法表达一致性要求）。                                                                                                                                                                                          |
| **运行版本基座（runtime base）** | CI 与本地测试（e2e 运行器 + vitest 的 node-pty TUI 用例）**实际加载**的 pi 版本；由 `npm ci` 装出的 **lock 版本**决定（`scripts/setup-ci.sh` 以它为唯一来源全局安装；`PIPELINE` 降级为**显式覆盖开关**，仅探测/排障才设）。_避免_：latest、当前版本。                                                                                      |
| **类型版本基座（type base）**    | `package.json` devDependency + `package-lock.json` 里供 `tsc`/vitest 编译期使用的 pi 版本；**必须与运行版本基座同版本**。_避免_：devDependency 版本、lock 版本。                                                                                                                                                                           |
| **基座提升（base bump）**        | 一次**显式提交**：同步抬升类型基座与运行基座到目标版本，并跑受影响模块回归。"跟随 latest" 的落地动作就是它（ADR-0063）。_避免_：升级、update（易与"用户在机器上 `pi update`"混淆）。                                                                                                                                                       |
| **latest 探测（latest probe）**  | **非阻塞**的定时（`schedule`）job：用金丝雀分片对**当前最新** pi 跑一遍，失败只产出"需要一次基座提升"的信号，不阻塞主流水线。_避免_：兼容性测试；_避免_ 与 **金丝雀分片**（本仓已专指 pre-push 里验证运行器改动的分片）混用。                                                                                                              |
| **基座消费者（base consumer）**  | 任何"实际跑的是哪个 pi 会影响其结果"的测试层：e2e 运行器（经 guard 解析 `E2E_REAL_PI`）与 vitest node-pty TUI 用例（`test/vitest/helpers/sandbox.ts` 的 `resolvePiBin()`：`PI_BIN` → npm 全局前缀 → PATH，**排除** `node_modules/.bin`）。同一提交的所有消费者必须跑同一基座（ADR-0063 决策 7）。_避免_：把 e2e 当成运行基座的唯一消费者。 |
| **跟随 latest（follow latest）** | 策略语义 = **不落后**（由 latest 探测承担早发现）+ **不隐式**（基座显式固定、提升是显式提交）。**不等于**"CI 每次装最新版"。_避免_：latest 漂移、自动升级。                                                                                                                                                                                |
