# ADR-0064: plannotator-tui——「变更」是选择器的候选集过滤，非差异视图；插件自持 git 层

**状态**：accepted（2026-10-24）

`/plannotator-tui` 的入口改成 /review 式的一屏目标选择后，三个决定会持续被后来者质疑，故记在此：①「未提交变更 / 某次提交」只是**搜索选择器的一层候选集过滤**，选中后打开**源文件**，不合成差异快照；② 终端批注能力**整体移除**；③ 候选集与选择器**自建**，不复用 `files` 扩展的 git 层。术语见 `CONTEXT.md` 的「plannotator-tui 评审入口」节。

## 决定这三件事的实测事实

以下事实来自 herdr annotate 插件自带的 `plannotator-tui` 二进制（v0.9.4）源码与实机验证，不是推测：

| 事实                                                           | 证据                                                                                                                                                                 |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一次只能打开**一个**路径                                       | `herdr open` 的 CLI 只接受一个位置参数，多给一个报 `unexpected argument`（实机验证）；源码 `cli.rs` 的 `path if open.path.is_none()`                                 |
| 文档模型是 **markdown**，不可切换                              | 渲染链是 `tui_markdown` + `pulldown-cmark`；`DocumentSource.content` 注释即 "Raw markdown"；官方定位 "Annotate Markdown in the terminal"                             |
| 文件夹模式的树**只列** `.md/.markdown/.mdx`                    | `tree.rs` 的 `is_markdown` 过滤；懒加载逐层，跳过依赖/构建目录与符号链接目录                                                                                         |
| 单文件模式**没有**文件树与文件名搜索                           | `app/mod.rs` 中只有 `open_folder` 会填 `tree`                                                                                                                        |
| 打开非 markdown 文件：排版被重排，但**行号回得到源文件真实行** | 对 81 行的 `.ts` 实测：块合并、缩进/空行丢失、长行折行（20 块）；但 `--annotate` 后 export 出 `(line 41)`，跨行选区出 `(lines 1–2)`——`srcmap` 把渲染行映射回源码偏移 |
| 批注粒度是**块**，块内可字符级选区                             | `--blocks` 一个围栏代码块 = 一个 `CodeBlock` 行                                                                                                                      |

关键推论：既然「一个路径」是硬约束，而她的强项是 markdown 文档，那么把「变更」做成**差异查看器**就得先合成 markdown 快照，再承担快照生命周期（谁清理、旧批注是否错贴、批注落在快照还是源文件）。而改造成本更低的语义是——变更只是帮你**找到那个文件**，评审仍发生在源文件上。

## 考虑过的选项

| 选项                                                       | 否决原因                                                                                                                                                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 变更 → 合成一份 markdown 差异文档再打开                    | 需要快照落盘与清理；批注锚定在快照而非源文件；与「文件选择器」成为两套交互，违背「整体交互统一」的目标                                                                                                  |
| 变更 → 合成临时目录（每文件一份 `.md`）用文件夹模式打开    | 能拿到原生多文件批注与合并发送，但同样有快照生命周期，且生成物路径与源文件脱钩                                                                                                                          |
| 统一选择器**多选**，逐个开面板                             | `plannotator-tui` 没有「上一个面板关闭」的信号，实际会瞬间弹 N 个覆盖层互相顶掉                                                                                                                         |
| 复用 `files` 扩展的 `git.ts` / `buildFileEntries` / 选择器 | 仓库此前**零**跨插件相对导入；`files` 的选择器是多选 + diff 快捷键，与本插件「一次一个路径」相反；其 `getGitStatusMap()` 的 Map key 是 porcelain 的**相对路径**、值与绝对路径比较，语义陷阱大于复用收益 |
| 保留终端批注（send / paste）                               | herdr 自带 `Ctrl+B Ctrl+V` / `Ctrl+B Ctrl+S` 覆盖同一场景；菜单保持最小                                                                                                                                 |

## 后果

- **多文件评审的唯一正道是「文件夹…」入口**（plannotator-tui 原生的多文件形态：树 + `Ctrl+P` 文件名搜索 + 一次合并发送）。单选约束要在 UI 文案上体现，别让用户以为能一次勾多个。
- **非 markdown 文件的屏幕阅读体验打折**（重排），但引用与行号是准的——不要据此"顺手"加一个"只能开 md"的限制，那会砍掉代码文件场景。
- 插件的 git 层是一份**有意的**重复实现：修 `files` 的 git 解析不会自动惠及这里，反之亦然。若将来出现第三个消费者，再考虑把 git 层下沉为共享模块。
