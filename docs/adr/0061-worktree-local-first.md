# ADR-0061: pi-worktree 本地优先——远端只提示，不动作

**决策**：pi-worktree 的**所有操作以本地 git 状态为唯一事实来源**。基点分支一律解析为**本地 ref**；**绝不隐式 fetch、绝不隐式改用 `origin/<b>`**。远端状态（ahead/behind、是否需要拉取）只作为**只读提示与建议**出现在结果/面板里，任何拉取动作必须由用户显式发起（显式写 `origin/<b>` 或显式 `--fetch`）。

## 与既有决策的关系（为什么不是重复造）

pi-worktree 的 `Local-First` / `Local Merge`（2026-08）已确立「不做远端操作（push 归用户）、merge 不自动 pull」。但那只覆盖了 **merge 路径**，**基点解析**仍是远端优先：

- `createWorktree`：`git worktree add -b wt/<name> <path> origin/<defaultBranch>`
- `execRebase`：远端存在即先 `fetch`，再 rebase 到 `origin/<onto>`

于是同一插件内出现自相矛盾：合并时本地优先、变基与创建时远端优先。本 ADR 不是新增原则，而是**把既有原则补齐到基点解析**——把远端降级为纯粹的只读提示。

## 为什么（触发这个决策的实测事实）

| 事实                       | 数据                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| 本地 `dev` vs `origin/dev` | 本地**领先 16 个提交**（`git rev-list --left-right --count dev...origin/dev` → `16 0`）      |
| 原 `createWorktree`        | 硬编码 `git worktree add -b wt/<name> <path> origin/<defaultBranch>`（`lib/worktree.ts:55`） |
| 原 `execRebase`            | remote 存在时先 `fetch`，再 `git rebase origin/<onto>`（`lib/git.ts:190+`）                  |
| `merge` 的落点             | 本地 `dev`                                                                                   |

于是原设计会产生**基点错配**：成员被 rebase 到 16 个提交前的 `origin/dev`（旧基线），却被 squash 合入本地 `dev`（新基线）——冲突在**错误的基线**上暴露（假冲突），或在旧基线上「干净」通过、合入时才炸。本仓库 `dev` 是**本地集成分支**（AGENTS.md：dev 永不 reset、连续开发；远端只在发版 `dev → main` 时参与），远端优先在这里是对着错误的事实做冲突消解。

## 被拒的替代方案

- **远端优先（原现状，也是同类工具的常见默认）**：仅在「基点即远端主干、本地只读」的仓库成立；对本地集成分支成立错误。
- **自动 fetch 保持新鲜**：把网络变成批量操作**中途**的可失败点（最难处理的位置：已合入一半），且让「一键」不再幂等——同一命令在两次运行间因远端变化而行为不同。

## 基点解析：解耦与派生（2026-09 补充）

`'main'` 在插件里同时是**主检出标识**与**目标分支默认值**（12+ 处字面量）——本仓库默认分支为 `main`、集成分支为 `dev`，两种语义互相遮蔽，缺省落点因此错到 `main`：

| 语义            | 位置                                                                               |
| --------------- | ---------------------------------------------------------------------------------- |
| 主检出 sentinel | `handlers.ts:437/537/1220/1527/1915`（`isMain = name === 'main'`）、`ui.ts:97-105` |
| 目标分支默认值  | `handlers.ts:310/1237/1536`（`targetBranch = 'main'`、`flags.target \|\| 'main'`） |

**决议：**

1. **解耦**：「主检出」用显式节点类型/常量判定，**不再用 `'main'` 字符串参与逻辑判断**。
2. **派生**（**禁止写死任何分支名**）——目标分支解析链，自上而下、全部落到**本地 ref**：
    1. 显式 `--target <branch>`
    2. 组的 `baseRef`（组场景）
    3. 仓库默认分支名（`git symbolic-ref --short refs/remotes/origin/HEAD` 去掉 `origin/` 前缀）→ 取其**本地同名 ref**
    4. 当前 `HEAD` 所在分支名
    5. 全部失败 → **报错要求显式指定，不猜**
3. 第 3 步只**读本地 ref**（不联网、不 fetch），与「远端只提示」不冲突；第 5 步存在的意义是避免「猜错落点」（猜错会把特性合进 `main`，是这类错误里最难发现的）。

## 后果

1. `create` / `rebase` 的基点改为**本地分支**（原有远端语义退化为显式选项）；`worktree add -b` 不再默认带 `origin/` 前缀。
2. 需要新增**远端状态提示**（提醒而非动作）：基点与 `origin/<base>` 的 ahead/behind 展示 + 建议文案，不触发任何网络请求——除非用户显式要求。
3. 这是**插件级原则**，适用于所有现有命令与未来命令；新增命令若想走远端，必须在命令面显式暴露。
4. 与「组」功能（显式花名册 + 仓库级声明 + `baseRef`）一致：`baseRef` 默认裸分支名 = 本地语义。
