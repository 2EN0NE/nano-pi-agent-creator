# ADR-0039: 目录绑定 agent 框架——人类操作台身份模型与健壮性补全

## 背景

ADR-0038 定稿后的实现评审发现三处「已定共识 vs 实现」偏差与若干机制缺口：

- `/org` TUI 看板被实现为「以打开目录的 agent 身份操作」，且全部动作（验收/打回/取消）校验 `dispatcher === 当前会话 agent` ——与 0038「人类操作全部可用、不限于本目录所属 org、人类最终裁决」矛盾；一旦派发人（可能是 member agent）离线或离开组织，**没有任何人**能验收/取消/改派 → 任务永久卡死。
- 握手「3 次退避重试」在无定时器扩展架构下物理上不可行（运行时 `setInterval` 不触发，AGENTS #13）。
- 对账三层触发只实现了手动层（事件增量/启动全量缺）；在线投递超时与 inbox 的边界模糊；跨进程读写同一任务文件无并发保护（铁终态可被旧快照回滚）；board 偏好存储偏离扩展配置规范。

## 决策

### 核心：TUI = 人的操作台（身份模型）

`/org` TUI 面板是**人**的界面，不是任何 agent 目录的代理。打开面板的人位于所有组织之上：

- 可浏览本机全部组织与任务（既有公司 tab 能力）；
- 面板上可见任务的**操作权不分 org、不分派发人**——任何僵死任务人都有通道收尾；
- agent 的命令面/工具（`/org approve`、`dispatch_task` 等）**继续严格限派发人**不变。

两条路径（人经 TUI / agent 经命令面）权限模型**彻底分离**，不再混用同一身份判定。

### 人类操作留痕（H1）

- 落账 `by` = `human@<打开面板的目录 basename>`（如 `human@jojo` / `human@chief`）——不记 agent 名，避免审计上把人的决策误读成 agent 行为；
- history 独立事件：`human_forced_approve` / `human_forced_return` / `human_forced_cancel` / `human_forced_reassign`；
- note 记录操作说明；验收记录 `acceptance.by` 同样记 `human@<dir>`。

### 人类动作集（F2）与语义

只开放四项（不做 adopt、不做「任意改状态」）：

| 动作 | 可用时机                               | 落账语义                                                                                                                                                                                         |
| ---- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 验收 | 任务**未关闭**皆可（不限于等待验收）   | 采纳全部已交付参与者、未交付参与者标停止、任务关闭——「人拍板收尾」                                                                                                                               |
| 打回 | 存在已交付参与者时                     | 已交付者全部拨回返工（轮次 +1）；无人可打回则提示、不落账                                                                                                                                        |
| 取消 | 未关闭皆可                             | 取消关闭；**铁终态对人也生效**（关闭后不可重开，与 agent 同一套终态规则）                                                                                                                        |
| 改派 | 子任务有焦点参与者且其状态非 delivered | 两级交互（G2）：详情页参与者行可聚焦 → 选目标成员 → 原参与者 cancelled（留痕「被人类强制改派」）→ 新成员以 invited 加入该子任务；子任务已无活跃处理人（全 rejected/cancelled/stopped）则直接加人 |

每个动作都经 TUI 二次确认弹层（按键 → 确认行 → `y` 执行 / `Esc` 取消）。

### 握手指引修订（D）

扩展无定时器，自动「3 次退避重发」不可行。修订为**惰性催办**：处理人会话启动 / 每次 org 操作后，若其名下有待确认的握手子任务（非负责人派发、invited 未决）→ 会话提示一次「有 N 个待确认握手请求（accept/reject）」。离线仍由 inbox 持久化兜底（不丢）。 **已落地（2026-09-13 销账）**：`remindPendingHandshakes`（并已按 ADR-0047 `D3` 加在岗门控——离岗会话不发面向模型的卡片）。

### 对账三层触发兑现（E）

- 事件增量 ✓（任务操作后投影，已有）；
- 手动全量 ✓（`/org reconcile`，已有）；
- **启动全量（补）**：成员进程 `session_start` 时对其所属各 org 执行一次对账，`done_without_delivery` / 超期 / 久置等 issues 以一条提醒消息呈现给会话。

### 在线投递分类（F）

`deliverMessage` 失败路径按语义区分：

- **connect 失败 / 进程不可达** → 落 inbox（离线兜底，任务不丢）；
- **已连上但回报超时** → **不谎报成功**：返回第三态 `uncertain`（tool 结果如实显示「送达存疑（未收到成员回报）」），**不入 inbox**（避免与「其实已入队送达」重复投递），并 log 告警。取舍：宁可由人看到"存疑"后决定是否重派，也不给出假的「在线送达」成功信号。

### 账本并发保护（G）

`saveTask` 写前比对磁盘 `updatedAt`：若磁盘时间晚于本次任务快照 → 抛冲突（不自动重试、不静默覆写）。命令/工具层捕获并转为友好提示「任务刚被他方更新，请重试」。目的：防止多进程 read-modify-write 把先写者的 closed 终态 / 交付记录回滚（铁终态与交付不丢在并发下的最低保障）。

### board 偏好存储（H；**2026-09-13 修订**）

**结论：迁入 `@zenone/pi-config`（用户级），原「保留 `.board.json`」的例外作废。**

- 现状：偏好存 `~/.pi/agent/extensions-data/org/config.json`（`org/config.ts` 的 `orgConfigStore`，用户级；项目级/会话级有意未启用）。

> **修订（2026-09-14，见 ADR-0051 D2）**：该文件不再只是「看板界面偏好」——它同时承载**行为默认**
> （成员启动参数初值 `memberLaunchArgs`），故模块级 store 由 `boardPrefsStore` 更名为 `orgConfigStore`。

- 理由：① AGENTS「扩展配置统一用 `@zenone/pi-config`」是**强制**项，而 board 偏好只有 `sortNewFirst`/`annotate` 两个布尔开关，不值得为其维持一条书面例外与一套自写 JSON 读写；② 「跨进程一致」由用户级文件天然满足（同一台机、同一 HOME 下所有面板读写同一份）；③ 原例外担忧的「测试隔离」改为**沙箱 HOME 隔离**（e2e 沙箱本就覆盖 `HOME`，vitest 在 `beforeEach` 里覆盖 `HOME`）。
- **取舍（已知代价）**：旧 `~/.pi/org/.board.json` **不再被读取**，升级后偏好回落默认值一次（不写迁移代码：仅两个界面开关，迁移成本高于收益）；`orgConfigStore` 是模块级单例且 `save()` 后缓存不再随 `HOME` 变化，故同一进程内跨 `HOME` 切换（测试场景）会读到缓存值——测试须在自己的 `HOME` 内完成断言。
- 参见：`extensions/auto/org/README.md` §1/§4 的配置文件位置表。

### TUI 看板视觉与人类管控（I）

**视觉规范**（`extensions/auto/org/board.ts`）：

- 标题行 `── org:<公司名> ──…`（嵌入顶边框）。第 0 行仅在 **Tab 切换公司**（显式上下文切换）时变更；同一公司内恒定——这是铁律 2「第 0 行不放随光标/滚动变化内容」的边界：**上下文切换型变更**允许，滚动/焦点型变更不允许。
- 四条横线：外框（顶/底）accent 满宽亮线；内部两条分隔线（tab 栏下、footer 上）**左空 2 格缩进 + dim 暗色**，形成主次层级。
- 成员行 `○ 名字 [负责人]  <工作目录>`：**行首四态圆点**（ADR-0040 D5：`dim ○` 睡眠 / `○` 空闲 / `accent ●` 工作中 / `●` 待验收），紧跟 `>` 选中位成固定 2 列；仅负责人带 accent 亮色标识；不展示 `manifest.label`、角色中文词、任务计数；目录 home 化 `~`、超宽保留尾部。
- **footer 逐屏据实**：footer 文案必须与该屏**实际可用的键**一一对应，不允许出现「该屏按了没反应」的键；代价是每屏一套文案（任务列表 / 任务空态 / 成员列表 / 成员详情 / 设置）。由此 `→` 不再在设置页兼任「执行」（`Enter` 才是执行，`←→` 全屏统一为切换视角）。

**成员详情**（成员视角第二级，成员列表 `Enter` 进入）：

- **标题行内嵌可感知状态**：`成员 <名>  <圆点> <状态词>  派发 n · 接收 m`（ADR-0040 D12②）。
- **诊断行**（标题下 1 行、`dim`）：在岗 `pid · 在岗时长 · tmux 会话名/手工启动 · 会话前 6 位`；睡眠 `已睡眠 · 上次会话 …`；进程在但未开 `--session-control` 时据实说明（ADR-0040 D7/B3）。
- **上下两区块** `派发（n）` / `接收（m）`：派发 = `dispatcher === 该成员` 的任务，接收 = 该成员出现在任一子任务 `assignees` 的任务。两区块数据独立、不联动。
- **每区块独立窗口**：单一 `↑↓` 光标跨两区块连续移动；**光标所在区块**窗口跟随光标（`start = clamp(cursor, 0, len - page)`），**另一区块**停在窗口首部（`start = 0`）。刻意不共享偏移——派发/接收是两条独立数据流，共享偏移会让「正在看哪条」失去判断依据。
- **每区块行数自适应**：`page = clamp(floor((rows - 12) / 2), 3, 7)`（`rows` 为终端高度，取不到时按 24）。保留 12 行给标题/tab/两条分隔线/两个区块标题/footer/溢出提示；常见 24 行终端 → **6 行/区块**，整屏约 20 行。
- 溢出渲染 `…余 n 条（↑↓ 滚动）`；空区块渲染 `无`；两区块皆空渲染 `该成员暂无派发/接收任务`。
- `Enter` 打开光标所选任务详情（两区块任一）；`Esc` 逐层返回**成员详情**（非任务列表）。

**交互修正**（用户旅程审查，判定标准 `docs/tui-interaction-patterns.md`）：

| #   | 问题                                                                                     | 修正                                                                                                              |
| --- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| P1  | 重命名公司不预填当前值、空回车报错（违反 §3.3「编辑必显当前值/空回车=保留当前值」）      | 进入输入态预填当前名；「空输入 / 未改动」回车 = 保留原名退出（不算错误）；标题显示 `（当前：<名>，直接回车保留）` |
| P2  | 成员列表、加入公司候选无溢出提示（成员数超窗口时用户不知还有更多）                       | 补 `…共 N 名成员（↑↓ 滚动）` / `…共 N 家公司（↑↓ 滚动）`，与任务列表、改派候选、成员详情一致                      |
| P3  | 确认屏用 `warning`+`dim`，破坏性后果视觉权重不足（偏离 §3.4「确认项用 error 强调后果」） | 标题 `error` 色、后果 `warning` 色                                                                                |
| P4  | 再次 `/` 搜索清空既有过滤（与 P1 同类的「凭空重写」）                                    | 进入搜索保留既有 `filter`，`Esc` 还原、`Enter` 锁定                                                               |
| P5  | 所有动作完成后 / 详情返回后光标跳回第一条（长列表批量处理体验差）                        | 新增下钻光标栈（`pushDrill`/`popDrill`）：进二级前记录一级光标位置，返回时恢复；切公司/切视角清栈                 |
| P6  | 列表高度固定 `MAX_BODY_LINES=10`，与成员详情的自适应不一致                               | 新增 `listRows()` = `max(10, min(30, maxTotal() - 8))`，随终端高度自适应                                          |

**人类管控动作**（F2 动作集扩展；全部二次确认，屏上可见「确认：… + 后果」）：

- **踢退成员**（成员视角 `d`）：人类强制 `leaveOrg`——移除成员、**保留回归档案**（history）、未结任务留在任务池待派发人改派；负责人不可踢退（先转移）、最后一名成员不可踢退。
- **负责人转移**（成员视角 `m`）：被指成员升 chief，原负责人自动降为普通成员；人类强制、被指者不可拒绝。
- **公司删除**（设置「删除公司」）：整树归档到 `~/.pi/org/.trash/<名>-<时间戳>/`（可人工恢复，不物理抹除）。
- **公司改名**（设置「重命名公司」）：迁移四处——目录 rename、`org.json.name`、`tasks/*.org`、`todo-map.json` 的 `entry.org`；成员工作目录不受影响；建议成员离线时改名。
- **加入公司**（设置「加入公司」）：用当前目录加入本机其他公司；命中历史回归冲突时引导改用 `/org join <名> --inherit|--fresh`。

**明确不做**：

- 「除名删历史」不做——回归档案的可追溯性优先；要彻底抹除请人工删除 `<公司名>/history/<成员名>.json`。
- 成员 `label/描述` 编辑不做（成员视图已不展示该维度）。
- 历史残留 `~/.pi/org/registry.json`（无任何代码读写）已删除，不留历史包袱。

**数据文件位置**：`extensions/auto/org/README.md` 为权威说明（目录树拓扑 + CRUD 矩阵 + 改名迁移清单 + 人工清理路径）。

## 后果

- 派发人限定不再是任务卡死原因——agent 路径权限不变，人的收尾通道独立可达；
- `human@` 进入可指认词汇：审计上一眼可辨「人干预」，且可溯源操作目录；
- 铁终态 / 返工轮次 / 交付可指认语义对人操作同样生效，不设第二套终态规则；
- 「成员详情 `Enter` 打开任务详情」曾**失效**：`renderTasks` 检查 `detailTaskId`、`renderPeople` 未检查，导致 `view === 'people'` 时详情永不渲染，且 `selIdx` 被归零（光标跳回区块顶部）；同时 `handleInput` 顶部详情分支已激活，`a/r/x/g` 会作用在一个看不见的任务上。已在 `renderPeople` 补同款详情委托修正，`Esc` 逐层返回成员详情；由 `test/vitest/extensions/org.board.test.ts` 的「Enter 打开所选任务详情」用例保护。
- 命令面 report/reject 省略子任务号已改为启发式回退（与工具层语义一致），待办投影文件名已对齐 todos 插件裸 hex（互操作）——两处为本评审期修复，行为随本文档记录归档。
- TUI 成为公司/成员全生命周期管控入口（C/R/U/D 齐备：建/查/改名/删、加/查/负责人转移/踢退）；数据文件位置与改名迁移清单沉淀于插件 README，视觉规范与管控语义沉淀于本文。
