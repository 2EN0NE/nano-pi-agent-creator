# ADR-0038: agent 框架选型——目录绑定 agent 实体，自有地基 + 模块级移植外部约定

- 状态：已接受（accepted，2026-09-08 最小原型验证通过）
- 相关组件：`extensions/auto/control`（会话间通信）、`extensions/security/sandbox`（OS 级沙箱）、pi 原生 cwd 上下文根
- 延伸：无（agent 框架首次立项）；与 ADR-0003（pi-lab 注册机制）、ADR-0025（bash 超时/工具干预）潜在相关
- 术语：见 `CONTEXT.md`（目录绑定 agent / 对等编排 / agent 家目录 / 存在边界）

## 背景

要构建「总决策 agent + 领域分工 agent」的多 agent 体系。核心诉求经过多轮对齐收敛为：**一个 agent = 一个目录**——在目录下启动 pi，该目录内的约定配置赋予 agent 名字、角色、能力、工具、上下文知识，并承载其记忆与资产；目录同时是未来沙箱（审计、黑白名单、网络/操作管控）的作用域锚点。这些目录 agent 之间是**对等编排关系**（双向/单向对话），而非父子从属。

曾考察五个外部子 agent 框架（`tintinweb/pi-subagents`、`nicobailon/pi-subagents`、`ak-pi-workflow-roles`、`pi-background-tasks`、`pi-dynamic-workflows`）。关键发现：**外部框架的子 agent 无一例外是「parent 会话内的 in-process child session」（父子、短命、共享进程）**，而本项目的模型是「目录绑定的对等实体」（独立存在、按需唤醒、目录即沙箱边界）。两者是不同物种。

进一步的代码调研发现：自有插件体系已经拥有该模型的三块地基——

1. **目录 = agent 存在**：pi 原生 `cwd` 即「上下文根」，`AGENTS.md` + `.pi/extensions` + `.pi/skills` + `.pi/agents` 均从 cwd 加载；
2. **agent 间对等通信**：`extensions/auto/control`（1929 行）已实现 Unix domain socket + `send_to_session` tool + `subscribe turn_end`，支持 steer/follow_up、单向/双向（wait turn_end）会话间通信；
3. **沙箱**：`extensions/security/sandbox`（329 行）已实现 OS 级 network（allowedDomains/deniedDomains）+ filesystem（denyRead/allowWrite/denyWrite）黑白名单，锚点天然可绑到目录。

## 决策

**不 fork 任一外部子 agent 框架作为基座，改为「自有地基 + 模块级移植」。** 基座 = pi 原生（目录=上下文根）+ 自有 `control`（对等会话通信）+ 自有 `sandbox`（沙箱）。外部框架的可指认/记忆/编排约定按**模块级移植**（借鉴其自包含的数据结构与字段语义），不移植其父子 in-process child session 核心，也不完全自研。

### 考虑过的选项

- **A. fork `tintinweb/pi-subagents`**：轻（2.1 万行）、session resume + memory 现成，但需从零补 mission/receipt/lane/intercom 半套「可指认性」框架，且子 agent 仍是父子 in-process 模型。
- **B. fork `nicobailon/pi-subagents`**：mission/receipt/lane/intercom/supervisor 现成，但 9.8 万行、日更多贡献者（追 upstream 成本高），子 agent 仍是父子模型，对等通信与 OS 级沙箱要另做，日志走裸 `console` 需桥接适配。
- **C. 自有地基 + 模块级移植外部约定**（采纳）：基座与「对等 agent 实体」模型天然对齐，复用自有对等通信与沙箱；外部框架的 mission/receipt/lane、agent frontmatter、编排原语等自包含约定按模块移植（借鉴源码），而非 fork 整个框架、也不完全自研。

## 验证记录（2026-09-08 最小原型）

用两个临时目录 + 自有 `control` 插件做最小闭环验证，两个地基假设均成立：

- **H1「目录=agent 存在」**：`agent-A/` 目录启动 pi 报出 `DECIDER-ALPHA-2026，总决策 Agent`，`agent-B/` 报出 `WORKER-BETA-2026，领域执行 Agent`——目录内 `AGENTS.md` 被正确加载为 agent 身份，零框架成本。
- **H2「对等通信闭环」**：A 经 `control` 的 Unix socket 发消息给 B，B 收到、以自身目录身份回复、触发 `turn_end` 回报，闭环成立。

发现一个非阻塞瑕疵：发送方 `--send-session-wait turn_end` 未真正阻塞等待 B 的回复（发送方 200ms 即退出，B 异步完成回复），「双向对话的同步等待」语义留待编排层实现时处理。

原型证据：`$TMPDIR/agent-proto/`（`README.md` 陈述问题 + 两个 `AGENTS.md` + `b.log` 完整证据链）。

| **TUI 任务看板**               | **`/org`（无参数）打开 TUI 面板**（人类管理台）；`/org <子命令>` 文本命令形式保留（agent / 脚本可用）。**不用泳道卡片**，改为：顶层**公司 tab**（tab 键切换本机全部组织，人类可浏览全部；当前目录可不属于该 org）→ 视角层 **[任务视角] [人员视角] [设置]**（←→ 切换）→ 任务视角下 **4 个状态子 tab：待办 / 进行中 / 等待验收 / 已关闭** → 列表（↑↓ 选行，回车进详情）。列表支持**日期时间排序**（创建 / 期望完成 / 最近更新）与**关键字搜索**；异常行带文字标（[超时][返工3][需改派]）。二级详情含子任务进度 / 交付内容 / 验收记录 + **人类操作**（验收 / 打回 / 改派 / 强制改状态 / 关闭）。 ⏳ _待续_：当前 TUI 人类操作仅对本目录成员名下任务开放，且收口在 `task.dispatcher`（验收/打回/取消/改派均需派发人身份）——「跨 org / 非派发人的人类强制入口（最终裁决者）」尚未落地，属后续实现项；人类强制操作不可依赖。**ESC 逐层返回，最上层再 ESC 关闭面板**。刷新：打开取最新 + **r 键手动刷新**，自动刷新为设置项默认关。可配置项（返工提醒阈值 / 超时提醒 / 待验收久置弱提示时长 / 界面偏好等）在**设置 tab** 查看与修改。 |
| **流程分支健壮性**             | 反向操作与边界已逐项敲定（见「取消与改派」「多人负责」「成员离开与回归」「期望完成时间超时」「返工上限」「派发人离线」「关闭即终态」「通用健壮性」各行）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **取消与改派**                 | 取消：任务无人领取 → 派发人直接撤；已有人在做 → **取消请求 + 处理人同意**（带原因留痕，处理人可交可不交已在做的部分）。改派：未领取 → 派发人直接改派，旧处理人待办该项标「被收回」；已领取/在做 → 不禁止，提供**改派 / 添加其他参与人**功能，**优先建议其他 agent 同步（并行）处理**。多人负责同一（子）任务的隔离语义见「多人负责」行。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **多人负责（情形 B）**         | 一个（子）任务可指派**多个子 agent 负责同一份内容**：参与者默认只看到自己负责的具体任务内容与期望完成时间，**不知道还有其他 agent 也在做**（知情隔离）。**子 agent 只对自己的交付负责，做完即报「已完成」，不感知、不等待他人**；派发人可能收到多份「已完成」消息。**最终算不算交付、采纳哪份、验收节奏全由派发人掌控**：可来一份审一份、可通过其中一份后**叫停其余参与者**、可等齐择优。叫停通知不点名他人，维持知情隔离。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **成员离开与回归**             | `/org leave` 先盘点名下未结子任务（进行中 / 已领未交 / 待确认握手）并让人类确认；确认退出后：已完成交付保留、未结子任务标记「处理人离开退回」回任务池，**派发人必须处理**（改派 / 关闭，不留挂起）。**离开后记录不删除**（历史保留，可指认）。**同目录同 ID 重新加入默认继承历史**；join 若发现该 ID 在 org 历史上存在过 → 提示并让人类手动三选一：**继承历史 / 清空重来 / 退出**（改 ID 后重新加入）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **期望完成时间超时**           | 期望完成时间可为空（空则无此逻辑）。超时 → 该子任务打 **「已超时」标记**（只加信息、不改流程状态）；**通知派发人一次**（催办 / 改派 / 取消由其决定）；**提醒处理人一次**（其工作台该项同步标超时）。不轰炸、不自动改状态。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **返工上限**                   | 不设硬性打回上限；每次打回累计**返工轮次**（留痕可指认）。同一子任务被打回满 **3 轮**后，后续每次打回都附加提醒派发人：「该子任务已返工 N 轮，可考虑当面沟通 / 改派 / 关停该子任务」。只提醒不拦截，质量决策始终在派发人。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **派发人离线（等待验收久置）** | 子任务交付后通知派发人失败（其离线）→ 通知进其**收件箱**，回来启动时呈现「你有 N 个待验收交付」。任务保持「等待验收」不自动变更（验收权不剥夺）。**人类强制入口扩展覆盖卡死场景**：人类在 TUI 可见「等待验收久置」任务（超过期望完成时间，或未设则超可配置时长）并可**强制验收通过 / 打回 / 改派 / 关闭**——人类是最终裁决者。（2026-09-13 **销账**：人类看板已具备 `human@` 身份与强制收尾——验收通过 / 打回 / 改派 / 取消，**不分 org、不分派发人**，见 `board.ts` 与 ADR-0039 §H1。）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **关闭即终态**                 | 验收通过并关闭的任务为**铁终态**：任何 agent（含派发人）都不能重开 / 修改 / 撤销关闭。发现漏检等问题 → 只能**新开任务**；新任务可**引用已关闭的旧任务记录**（追溯漏检来源、带返工上下文），但旧记录本身不可动。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **通用健壮性**                 | ①**重复操作幂等**：同一交付 / 确认 / 验收消息重复到达只生效一次（任务 + 动作判重），已交付过再次报告提示不重复计。②**任务编号**：org 内唯一，**字母 + 数字混合、位数多**（如 8 位随机风格，不用短递增数字，避免用尽与撞号）；删除不复用。③**org 删除与改名**：人类可删除整个 org，删除前数据归档（挪到可恢复备份位置，不物理抹掉）；org 名创建后不改名（改名 = 新建 + 迁移留档）——**2026-09-13 由 ADR-0039 取代**：已提供**原地改名**（`/org rename` / 看板「重命名公司」，迁移目录 + `org.json.name` + 全部 `tasks/*.org` + `todo-map.json`），不再走「新建 + 迁移留档」。                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## 后果

- **cwd 语义确立**：cwd = agent 的**存在边界**（身份/能力/知识/记忆/资产/沙箱作用域），区别于「工作目录」「进程 cwd」「上下文根」等旧用法。未来代码与文档统一此义。
- 对外部子 agent 框架的评估结论落定：`nicobailon/pi-subagents` 是最成熟者，但其「父子 in-process」模型与本项目「目录绑定对等实体」不兼容，故**模块级移植其自包含约定（agent frontmatter/memory/mission/lane）**，不 fork 整个框架、不完全自研。
- 沙箱方向明确复用自有 `extensions/security/sandbox`，后续在其上扩展审计与算法级管控，而非新起炉灶。
