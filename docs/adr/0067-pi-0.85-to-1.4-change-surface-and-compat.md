# ADR-0067: pi 0.85 → 1.4 的变更面评估，与「版本能跑 ≠ 语义对齐」的处置清单

**决策**：把 0.85 → 1.4 这一段上游变更**按"破坏面 / 命中点 / 处置"三列**固定下来，用来关闭 ADR-0063「待验证」清单；同时确立一条口径：**基座提升的验收不只是 `tsc` + e2e 变绿，还要逐条核对"插件写的语义假设"是否仍成立**——本轮找到的 4 项问题全部属于后者（类型层全绿、运行不报错，但结论失真）。本 ADR 只做记录与决策，**不改代码**；实施项见「实施状态」。

- 状态：**已接受（决策采纳，实施项待办）**（2026-10-25）
- 相关组件：`extensions/context/smart-context`、`extensions/context/custom-compaction`、`extensions/tui/quit.ts`、`extensions/meta/preset`、`themes/*.json`、`AGENTS.md`「开发 Pi 插件一些补充信息」节
- 上游 ADR：[`0063-pi-version-base-and-latest-probe.md`](0063-pi-version-base-and-latest-probe.md)（基座双层固定 + latest 探测，"待验证"清单在此结案）

## 背景

ADR-0063 在 1.2.0 基座提升时留了一张「待验证（1.2.0 的破坏性变更清单，按 dist/文档读出的候选，尚未逐条实测）」表，随后基座升到 1.3.0、全局运行层到 1.4.0，该清单一直未逐条实测。本轮把它做完，并把范围前推到 0.85（本仓最早适配过的分界，`AGENTS.md` 里 `pi-tui ≥0.85` 的说法即源于此；更早的基座是 0.84.4）。

### 取证方法（可复现）

```bash

npm pack @earendil-works/pi-coding-agent@0.85.0 @earendil-works/pi-coding-agent@1.4.0 \

# 2) 逐版本读 CHANGELOG 区间（0.86.0 … 1.4.0，含 0.87.1→0.99.0 的跳号）

diff .../0.85.0/dist/core/extensions/types.d.ts  .../1.4.0/dist/core/extensions/types.d.ts

```

## 结论（三条）

1. **1.3.0 → 1.4.0 对扩展开发者是零 API 变化**：`pi-coding-agent` 的 `dist/index.d.ts` 与 `dist/core/extensions/types.d.ts`、`pi-tui`/`pi-agent-core` 的 `dist/index.d.ts` 与 1.3.0 **逐字节相同**；`pi-ai` 仅 `+2` 行新增导出（`./utils/identity`、`PI_AI_VERSION`）；`pi-tui` 仅在 `terminal/tui/tui-alt-screen` 加**可选** `restoreOnExit*`（进程 `exit` 兜底恢复终端模式）。→ **基座提升到 1.4.0 没有类型风险**。
2. **0.85 → 1.x 的破坏面只有四处**（0.86.0 / 0.87.0 / 1.0.0 / 1.2.0），且都是"语义变化"而非"接口删除"：`ExtensionAPI` 只增不减（+7 个方法），`ExtensionContext` / `ExtensionCommandContext` / `ExtensionUIContext` 的接口体 0.85 与 1.4 **完全一致**。所以项目大量 `ctx.ui.*`、`ctx.compact()`、`ctx.newSession()` 用法不受影响。
3. **本轮命中 4 项**：2 项是**真缺口**（代码仍按旧语义写，且本仓内有真实触发路径），2 项是**口径过期**（不报错，但统计/文档结论失真）。另有 8 项「可白拿能力」与 3 处「结构性重叠」登记为候选，不在本轮做。

## 需要处置的四项

### B1（真缺口）`smart-context` 在「自定义消息触发的 run」上会抛错

- 位置：`extensions/context/smart-context/src/index.ts:75` → `router.pick(event.prompt, ctx)`；`src/router.ts:98` 直接 `prompt.slice(0, 100)`。
- 原因：1.2.0 起 `before_agent_start` 是 `messageType` 联合，`"custom"` 分支**没有 `prompt`**；`pi.sendMessage(..., { triggerTurn: true })` 在 idle 时也走该事件。
- 触发路径**在本仓真实存在且由项目自己产生**：`context/goal.ts:585`、`auto/loop.ts:254`、`auto/control/index.ts:801`、`tui/answer.ts:639`、`auto/org/index.ts:576` 都是 `{ triggerTurn: true }` 的自定义消息。
- 后果：`prompt.slice` TypeError；**错误不是静默的**——插件自己 `catch` 后 `ctx.ui.notify('smart-context 路由错误…', 'warning')`，所以 loop 每跑一轮就弹一次 warning toast，并在日志留一条 ERROR。
- 加重因素（已在本轮修掉）：该插件曾被 `tsconfig.json` 的 `exclude` 排除，**永远不会被 `npm run typecheck` 抓到**；且它 `package.json` 里钉着 `@earendil-works/*@^0.79.4` 的 devDependencies，sync 时会在目标目录 `npm install` 出一份 0.79.x 类型副本 —— 任何人在那里跑 `tsc` 都会对着 0.79 的 `event.prompt` 判断"没问题"。`enabled` 默认 `true`（`src/index.ts`），本仓 `.pi/extensions-data/smart-context/config.json` 有 active 配置 → 是活路径。
- 修法与口径（决策 1 的细化）：`"custom"` 分支**跳过分类**并保留**大上下文阈值保护**（该判断位于分类器调用之前、与 `prompt` 无关）。**不**按 `message.content` 重新分类（会在任务中途降档/跳模型并丢 prompt cache），**不**做 `customType` 白名单（会让本插件认识具体消费方）。

### B2（真缺口）`custom-compaction` 的摘要输出上限与 1.4.0 语义脱节

- 位置：`extensions/context/custom-compaction/compactor.ts:295` → `maxTokens: overflowRecovery ? 2048 : 8192`（硬编码）。
- 上游正是 1.4.0 改的点：「compaction 与 branch summary 改用模型的 output limit，长推理不再让摘要失败」。项目自建摘要仍钉 8k → 长会话/推理模型上会 `stopReason: length`，出现「内置压缩成功、自定义 profile 失败」的分裂行为。

### C1（口径过期）`quit.ts` 的用量聚合漏 `usage` entry

- 位置：`extensions/tui/quit.ts` 的 `usageOfEntry()` 与 `aggregateModelUsage()`（两处独立实现）只认 `message`/`compaction`/`branch_summary`。
- 上游官方口径（`pi-coding-agent/dist/core/usage-totals.js` 的 `getUsageCostBreakdown`）多一类：`entry.type === "usage"` → 按 `${provider}/${model}` 归桶。
- 后果：`cache_warm`（0.86.0 起的缓存保温）产生的费用不计入，与内置 footer 对不上——而该函数注释自称「对齐内置 footer」。
- **同类第二处（原 ADR 漏记）**：`extensions/observability/session-analytics.ts` 只认 `type === 'message'`，`usage` / `compaction` / `branch_summary` **三类全漏**（无条件触发：任何压缩过的会话都被低估）——比 quit 的 `usage` 缺口更常撞上。
- 实际触发面（实测）：`usage` 记录要求"请求可重放 + 模型暴露 prompt-cache TTL + 成本可算"，本机近期 763 个会话中 **0 条** `usage` 记录 → 该缺口在当前 provider 组合下**休眠**，但对暴露 cache TTL 的官方 provider 会真实发生。故本条理由是**口径一致性**，不是当前失血。

### C2（口径过期）`AGENTS.md` 的「`compact()` 内部事件时序」与源码不符

- 文档称 `_disconnectFromAgent()` → `session_before_compact` → `session_compact` → `_reconnectToAgent()`。
- 实测 1.4.0：`_disconnectFromAgent()` **只在 `dispose()` 里调用**；`compact()` 全程不断开 agent。**0.85 同样如此** → 这条知识从一开始就与源码不符，不是版本漂移。
- **但结论必须保留**（原 ADR 写的"降级为保守建议"是错的订正方向）：`prompt()` 在压缩进行中直接 `throw new Error("Cannot submit a prompt while compaction is in progress. Wait for compaction to finish and retry.")`，而压缩控制器要到 `session_compact` 派发**之后**才清除 → 在 `session_compact` 里发消息是**确定性失败**，不是"过度保守"。`compaction_end` 那条"listeners may submit queued prompts"注释指的是会话内部 emitter，**不是扩展事件**。
- 后果（订正后仍是"必须知道"）：正确结论 = 理由换新、结论不动。附带两条同源过期知识一并订正：`isIdle()` 实现已不是 `!isStreaming`；`sendUserMessage` 的失败**不再被静默吞掉**（经 `runner.emitError` → `showExtensionError`，用户看得到错误框）。

## 结构性重叠（需要"决策"，不是"修 bug"）

- **E1 工具权威**：pi 已自带 `defaultTools` + `+/-` 修饰 + resume 保留活动集（1.1.0/1.3.0）+ `defaultActive` + `exposure`。preset 的封闭集是**自建的一层**。ADR-0065 的复位语义目前与 pi 一致，但**上游每加一条默认选策规则，就多一个需要同步的点**——1.1.0 与 1.3.0 就是本轮新出现的两个同步点。
- **E2 请求级模型路由**：`smart-context` 与官方虚拟模型职责重叠；若采纳虚拟模型，B1 随之消失（问题从"修守卫"变成"删自建层"）。
- **E3 重试**：pi 1.4 的可重试模式含 `429/500/502/503/504/520/524`（`pi-ai/dist/utils/retry.js:36`），`auto/pi-rate-limiter` 另有自建 429 节流 + `rate-limit-retry` 分支重试。两条链叠加时的行为**无用例覆盖**。

## fullscreen 实测（TUI 覆盖层）

**前提纠正**：`tuiMode` 默认 fullscreen 不是 1.4 才有的——pi CHANGELOG 记在 `## [1.0.0]`（"Changed the default TUI mode to fullscreen"），`settings-defaults.js` 在 **1.3.0**（本轮实际核对的版本）亦为 `tuiMode: "fullscreen"`，且本机 `~/.pi/agent/settings.json` 显式设了 fullscreen。所以 6 处 `overlay: true` 与 5 处"按 `terminal.rows` 算高度"的 UI **一直在 alt-screen 渲染器下运行**——这不是待验证的升级风险，而是既成事实。

**实测结论（1.4.0 基座）**：

| 检查                                              | 结论                                                                                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6 个覆盖层的 TUI e2e                              | 全 PASS（quit 5、answer 3、btw 2+1 REVIEW、pi-shortcuts 4+2 REVIEW、permission-gate 19+3 REVIEW、pi-rewind 4）                                       |
| 按 `terminal.rows` 算高度的 5 处                  | 全部以 `terminal.rows` 为上限（`rows - N` 或 `min(…, rows-8)`），**不可能超出视口**；覆盖住底部输入区属模态覆盖层的标准行为（pi 自带选择器同样如此） |
| TUI 合规门禁（`scripts/check-tui-compliance.ts`） | 通过（无双宽 emoji、无硬编码颜色、`truncateToWidth` 兜底齐备）                                                                                       |
| `AGENTS.md #13`（fullRender 重影铁律）            | 仅 regular 模式适用；fullscreen 走 alt-screen 整屏重绘，`firstChanged < prevViewportTop` 那套不适用 → 已在 AGENTS.md 加模式限定                      |

**未覆盖（知情接受）**：没有为每个覆盖层单独写"遮挡输入框"的几何断言——那需要为 6 个组件各搭一套 fake 生命周期，成本远高于收益；现有 TUI e2e 已覆盖"能否正常渲染 + 关键文本可见 + 不崩溃"。

## 被拒方案

- **"跟到 latest 就完事"**：1.3→1.4 恰好 API 零变化，这次侥幸不代表通用；本轮 4 项全部是"编译通过、跑也不报错、结论却错"的类型，只有逐条核对语义假设才发现。
- **按住 B1 不管**（"反正只影响自定义 run 的路由"）：触发源正是本仓自己的核心链路（loop/goal/org/answer），且**每轮都会弹一条 warning toast**（不是静默）。
- **把 C2 订正成"保守建议"**：这是本轮差点走成的错误订正方向——理由（agent 断开）确实是错的，但结论（只能在 `onComplete`）由 `prompt()` 的压缩中守卫**强制**成立；若降级为建议，后续开发者会照新措辞在 `session_compact` 里发消息并静默失效。
- **B2 直接对齐 1.4 的"无上限"**：`overflow` 恢复路径仍应保留小上限（1.4 也保留 `willRetry` 分支的差异化行为），否则重试期更易二次溢出。
- **把 preset 权威整体让给 pi**：`exposure`/`defaultActive` 能表达"注册即非激活"，但表达不了"激活期封闭集 + 子工具锁死"（ADR-0049 的核心约束）；本轮只登记同步点，不换实现。
