# ADR-0058: permission-gate 提升建议 —— 产物落在用户级配置，不做策略层搬迁

**决策**：permission-gate 新增「提升建议（promotion suggestion）」机制：插件从真实历史归纳出候选，建议把某条放行原则的**作用范围**从当前项目扩大到用户级 / 多个项目；候选**不自动生效**，由人类在面板的**首个 tab**（「设置」→「提升建议」行；快捷键 `p`）逐条查看证据并确认。**提升的产物一律是用户级 `config.json` 的类别条目**（临时区/安全根、工具+目标范围、`dynamicPolicy` 的 scope 列表等），**不做策略层（manual-strategies / graduated 计数）的跨层搬迁**。

## 为什么：key 可移植性决定了"搬迁"这条路走不通

现有三类 grant 的匹配 key 里，只有两类可跨项目复用：

| key 形态                   | 跨项目可移植   | 依据                                                         |
| -------------------------- | -------------- | ------------------------------------------------------------ |
| `cmd:<hash>`（整条子命令） | 否             | hash 含项目绝对路径；115 次真实拦截中精确重复的子命令仅 4 类 |
| `dir:<绝对路径>`           | 否（例外见右） | 唯一例外是 `/tmp`、`~/.cache`、`~/.pi/...` 这类全局共享根    |
| `tool:<名字>`              | 是，但极粗     | "rm 全局可信"；单会话内 `tool:rm` 计数曾达 18                |
| config 条目                | 是             | 天生与项目无关                                               |

因此"把项目级策略原样搬到用户级"（选项甲）对绝大多数条目是**空操作**——这不是偏好，是可从数据推出的事实。类别条目（选项乙）天生与项目无关，是唯一能表达"rm 删除 临时区根下路径"这类可跨项目复用信任的载体。

## 考虑过的选项

- **甲 策略层搬迁**（move 到用户层，key 不变）——否决：**受 key 粒度所限**。三类 grant key 里只有 `tool:<名字>` 跨项目可移植（见上表），`cmd:<hash>`（hash 含项目绝对路径）与 `dir:<绝对路径>` 搬到用户级后，新项目不会命中同一条 key，**等于空操作**。反过来，`tool:` 键搬迁虽有效，却是「rm 全局可信」式的**极粗**信任（单会话内 `tool:rm` 计数曾达 18），风险远大于收益，故不作为跨项目复用的载体。需注意：采纳时会话内产生的新计数**仍会迁到用户层**（`tool:` 键），其范围由 **tier 门禁**（critical/提权/凭证永不迁层）与**出处条件**兜底——跨项目复用的正载体是乙（配置层类别条目），不是搬 key。
- **乙 配置层类别条目**——采纳。
- **丙 `dynamicPolicy.scope` 列表化横向扩面**——采纳为乙的**一种条目形态**（"把某项目根加入 scope 列表"），不单独成为机制：scope 是包含性边界（目标路径必须落在 scope 内），直接放宽到 `~` 等于让 tool/folder 维度全局毕业，风险大于收益。
- **丁 两类产物分流并存**——否决：落盘位置不同会让"确认"这一步的语义分裂，增加误操作面。

## Consequences

- 提升会修改**影响所有项目**的判定规则 → 必须人工逐条确认、可撤销、每条候选带证据（跨几个项目、批准/拒绝次数、最近时间）。
- 与 ADR-0025 的「危险等级越高，信任越不持久」存在张力，用两条硬约束兜住：①**提权与凭证类永不进入候选**（无论次数多少）；②只有经危险分级重划后属"局部可逆"的类别（如 临时区根写）才有提升资格。
- 既有术语冲突待统一：preset 已有「提升（promote）」= 会话级 preset 按键写项目级 config，且**不提供到用户级的 TUI 路径**。本 ADR 只定义 permission-gate 侧；跨插件统一提升范式另议（见 `CONTEXT.md` 的 **提升建议** / **提升** 两条术语）。

## 补充（触发点：当场发现，而非事后扫历史）

初稿把候选来源写成「插件从真实历史归纳」，主要露出面是面板首个 tab。修正为：

- **主触发点 = 用户完成一次权限选择之后**（那一刻用户在场、手里有上下文），且必须**事件驱动**（`tool_result` / `turn_end` / `agent_settled`）——不能用定时器（本仓 AGENTS.md 坑 #13：扩展运行时 `setInterval`/`setTimeout` 回调不执行）。
- **提示不阻塞 agent**：`ctx.ui.notify()` / `setStatus()` / `setWidget()`；细节确认由用户主动打开 overlay。
- **面板 tab 保留为归档 / 浏览 / 撤销入口**，不再是唯一发现路径。
- **键的泛化层级由用户当场选**（叶子向上的台阶，默认最保守的「具体路径」）——见 ADR-0060 的修正节。

**理由**：算法预判「这条属于哪一类」要在热路径上承担误放行风险；把泛化交给在场的人看**具体例子**再定层级，既更准也更省。这也解掉了「新 tab 上线初期是空的」这个顾虑——提升不再依赖事后扫历史。

## 补充（现场触发条件；deny 拆分降级）

**触发条件 = 「本会话人工放行次数 ≥ 阈值（cmd 2 / tool 3 / dir 4）** 且 **自动放行次数 = 0」**。

即：同一类操作已经被**人工**放行了足够多次，却**从未**自动放行过——这才是「机制记不住、该提升了」的现场证据（例：目标在信任范围外，或目标是变量因而不匹配任何键）。

**连带调整**：`docs/adr/0059-trust-scope-is-directory-scoped.md` 原本给范围提升定的门槛「≥2 个目录 + ≥3 个不同会话 + 0 次真拒绝」**不再是硬门槛**——那是给「事后扫历史」设计的门槛，搬到现场会问得太晚、太抽象。跨目录/跨会话统计降级为**卡片上展示的证据与置信度**。

**因此 `deny` 拆分（拒绝 / 无界面自动拦 / 旧数据迁移）从「前置依赖」降级为「观测改进项」**，不再阻塞本机制；但仍应做——拒绝历史要作为证据显示在卡片上（「⚠ 这条模式在别的会话被拒绝过 2 次」），否则用户可能提升一件自己以前明确拒绝过的事。
