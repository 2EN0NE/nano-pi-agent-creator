# ADR-0042: 在岗简报——把"使用 org 所需的知识"注入在岗成员的会话

- 状态：**已接受**（2026-09-11）
- 相关组件：`extensions/auto/org`（`index.ts` 生命周期、`orgstore.ts`、`board.ts`、`manifest.ts`）、`scripts/sync-to-local-pi.ts`（内嵌技能分发）、扩展 manifest 的 `pi.skills`
- 延伸：落实 ADR-0041 `D2` 的"技能门控"；向 `CONTEXT.md` 补术语
- 术语：见 `CONTEXT.md`（多 agent 框架节：在岗简报 / 成员简介 / 在岗）

## 背景

在岗成员原先**不知道**自己属于哪个 org、有谁在岗、组织是干什么的、有哪些可用技能——一切都靠 agent 主动调 `org_fleet`。而"要不要主动查"这一步是**隐式的**：技能描述里虽写了"先感知"，但没有名册，agent 无从判断是否需要。

同时，`pi` 的系统提示是 **prompt cache 的断点**（`docs/models.md:479`：`cache_control` 打在系统提示、最后一个工具定义、最后一段 text content 上）。系统提示位于消息之前，因此**系统提示每轮变化 → 整条前缀（含全部对话）缓存全量失效**（Anthropic 系缓存读 0.1x vs 全新输入 1x，量级差 10 倍）。"每轮动态拼接进系统提示"这个直觉方案代价极高。

## 决策

### D1 在岗简报 = 静态块 + 动态块

- **静态块**：① **定位**（所属 org / 角色 / 成员简介）、③ **组织背景**、⑤ **可用技能指路**；
- **动态块**：② **在岗成员**（名字 + 状态）、④ **最近动态**（未结任务、未读 inbox 计数）。

仅 **在岗** 进程获得；未在岗进程既无简报、也无 org 技能。

### D2 静态块进**系统提示**，会话内恒定

由 `before_agent_start` 恒定追加。语义上"我是谁 + 行为指路"属于 system；内容会话内**不变** → 系统提示逐轮一致 → **cache 稳定**；且不占用会话消息位。

### D3 动态块追在**用户轮次尾部**，每轮都追加

经 `input` 事件的 `transform` 改写用户消息（`docs/extensions.md:911-955`；范例 `examples/extensions/input-transform-streaming.ts` 即"往用户消息尾部追加 `git diff --stat`"）。

**关键性质**：transform 发生在**消息持久化之前** → 追加内容**随消息存进会话** → 下一轮 payload 的前缀与上一轮**逐字节一致** → **prompt cache 不受影响**。这是本决策成立的**唯一理由**（否则每轮改系统提示将付出约 10 倍输入成本）。

- **每轮都追加**：确定性最强（尾部永远有最新块，不必回看历史）；
- 块内**只含名字 + 状态 + 一行计数**，**不含成员简介**（挑人派活是低频决策，调一次 `org_fleet` 即可）。

### D4 技能"只指路"，正文按需 `read`

简报里只写技能名与适用时机（按角色给 2–3 行），**不内嵌技能正文**——技能门控落地后 `resources_discover` 已让 pi 把技能 name + description 常驻系统提示（progressive disclosure），简报再抄一遍就是**重复且会漂移的第二份真相**。

**落地方式**：扩展 manifest 不再声明 `pi.skills`（否则 sync 会把技能装进全局 `skills/`，所有 pi 都能看到）；技能随扩展目录分发，运行时由 `resources_discover` **仅在岗时按角色**贡献路径——负责人 → `org-chief`；成员 → `org-member`；两者都附 `org-recover`（少数情况下如何解卡）。

### D5 组织背景存 `org.json` 的 `background`

自由文本（超长在看板内折行显示）、**可选**。编辑入口 = 看板设置页新增一行「组织背景（本组织）」，Enter 进入**看板内输入态**（**预填当前值**，遵循编辑心智 §3.3；清空后保存 = 删除该字段，Esc = 取消不写）。作用域与 `autoWake` 同级（ADR-0040 D8 先例：org 级设置存 `org.json`，不进插件配置）。创建 org 时**不做必填**。

### D6 成员简介的快照刷新三时机

`org.json` 的 `member.manifest` 是 join/create 时的**快照**，原先**没有任何更新路径**。刷新规则：

1. **在岗注册**时成员回写自己的（← 当前 `pi.agent.json`）；
2. 看板按 `r` 刷新时**重读全体**成员目录并回写（**人类显式动作**，不违反 ADR-0040 D4「感知与动作分离——巡检不写副作用」）；
3. 渲染在岗简报时**实时重读**，但**只读不回写**。

③ 只读的理由：每轮回写会让"渲染简报"这个感知动作产生写副作用；且 `org.json` 是**整文件读-改-写**，多成员每轮并发写会**丢更新**。

### D7 TUI 展示（成员简介）

- **成员列表**：在「名字 + 标签」与「目录」之间加一列简介缩略，**20 显示列**（超出取 19 列 + `…`，不足补空格以保证目录列对齐，空显示 `(无)`）；窄终端降级：**< 100 列 → 10 列**，**< 80 列 → 隐藏该列**；
- **成员详情**：头部下加一行 `简介：`，折行显示**全貌**（不截断），空显示 `（未填写）`。

## 后果

- **正向**：在岗成员一启动就知道"我是谁、有谁在、组织在干什么、有哪些技能"；动态块不牺牲 prompt cache；技能保持单一真相（正文只在技能文件里）。
- **负向**：动态块会**成为用户消息的一部分、在 TUI 中可见**（人类会看到每轮尾部的状态块——与 git-diff 类插件同源）；且它**随会话历史累积**（长会话里会堆到几十行）。必要时后续可加"超过 N 轮只保留摘要"的增量优化。
