# ADR-0020: TUI 交互模式三轴分类与规范落地三件套

- 状态：已接受（2026-08-17）
- 相关组件：`docs/tui-interaction-patterns.md`、`src/`（后续脚手架）、全体 TUI 扩展

## 背景

现有 TUI 规范 `docs/tui-design-principles.md`（571 行）聚焦视觉与布局（边框、颜色、对齐、按键），
缺少「交互层面」的约定——面对一个 UI 任务，开发者不知道该选哪种结构。30+ 带 UI 的扩展里三种
实现方式并存（手绘字符串 / Container 组件树 / 自定义 Focusable 组件），且暴露交互缺陷：
pi-lab 面板把「选实验」和「选操作」拍平为每实验内嵌一个 SelectList，高度随实验数线性膨胀，
焦点管理失效（`activeSelectListIndex` 恒为 0，`Tab` 被标签切换占用，后面的实验永远选不到）。

## 决策

1. **三轴正交分类**取代「按场景一维列表」。TUI 设计按三个正交维度组织：
    - 轴 A 入口：`setStatus` / `setWidget` / `custom`(overlay) / `setHeader`/`setFooter`
    - 轴 B 交互模式：只读展示 / 导航选择 / 表单编辑 / 确认菜单
    - 轴 C 实现策略：手绘字符串 vs 组件化（Container 组件树）

    「custom 手绘 vs Focusable 组件」不是同一层级对比——`custom` 是入口（所有 overlay 都走它），
    `Focusable` 是横切能力（`focused: boolean` + `CURSOR_MARKER` 硬件光标定位），实现策略才是真正的分叉。

2. **导航选择交互强制 master-detail 两级导航**：一级列表（选中 → 详情），一级列表必带滚动上限。
   禁止把操作菜单与导航列表拍平在同一级。

3. **规范落地三件套**：文档（`docs/tui-interaction-patterns.md`）+ 规范检查器（挂 semgrep/eslint，
   把禁令变成可执行 gate）+ 脚手架生成器（scaffold CLI，规范稳定后做）。`/src` 只放 dev-time 工具，
   插件运行时零依赖（插件保持独立）。

## 权衡

| 方案                             | 结论                                                                        |
| -------------------------------- | --------------------------------------------------------------------------- |
| A. 单一推荐架构（全部组件化）    | 拒绝：answer.ts 复杂布局手绘更自然，强行收敛让部分场景别扭                  |
| B. 三轴正交 + 场景绑定（本决策） | 采纳：保留多种实现，但明确「什么场景用什么」，底层契约统一（Component）     |
| C. 纯文档（不做检查器/生成器）   | 拒绝：571 行文档已存在，但 answer.ts 硬编码颜色、btw.ts 用 emoji 仍无人纠正 |

## 后果

- **正向**：新扩展有明确的「对号入座」路径（选入口 → 选交互模式 → 选实现）；交互缺陷有 gate 兜底。
- **负向**：三轴模型比一维列表更难记忆，需在 AGENTS.md 放铁律摘要；检查器规则需随规范演进维护。
- **注意**：`Focusable` 是横切能力而非分类维度——手绘与组件化均可选加，不改变入口与交互模式。
