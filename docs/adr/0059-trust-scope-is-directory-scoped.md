# ADR-0059: 信任范围以目录为单位（与项目身份 projectKey 分离）

**决策**：permission-gate 的**提升建议**以**目录**为触发与产物单位——同一 `projectKey`（仓库）下 **≥2 个不同目录**、**≥3 个不同会话**、**0 次真拒绝** → 产出「**范围提升**」候选（把目录根写进用户级 scope 列表）；跨仓库的「**层级提升**」（写用户级 config 类别条目，见 ADR-0058）保留为第二条轨道，门槛是 ≥2 个 `projectKey`。配套把 `dynamicPolicy.scope` 从单个绝对路径改为**列表**。

## 现状确认（非本轮引入）：系统里有两套并存且刻意不统一的身份

|                       | 取值                                                                      | 用途                                       | 粒度                             |
| --------------------- | ------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------- |
| 项目身份 `projectKey` | `git remote get-url origin` 的 SHA256 前 12 位（无 remote 退回路径 hash） | 审计归档、历史/策略面板按项目过滤          | **仓库**（同仓库 worktree 共享） |
| 信任范围 `scope`      | 单个绝对路径                                                              | 动态策略判定（cwd 与目标路径都须落入其中） | **目录**                         |

## 为什么提升必须按目录（数据依据）

真实记录里 `rm -rf "$VAR"`（「删自己临时目录」的典型形态）分布在**同一个仓库**的 3 个目录：`worktrees/tool` 15 次 / 3 会话、主仓 6 次 / 2 会话、`worktrees/observability` 4 次 / 2 会话。

- 按 `projectKey` 计：这 3 个目录是 **1 个项目 → 0 条候选**，机制空转（用户 90% 的记录都在这一个仓库里）。
- 按目录计：3 个目录、7 个会话 → **触发**。

同时，6 个 worktree 的 `.pi/extensions-data/permission-gate/config.json` **各自把 `scope` 写死成自己**（context / verification 未写，取默认 `.`），使信任在目录间完全不通——这正是「同一个行为被三个目录分别重新问一遍」的来源。

## Consequences

- `scope` 列表化后必须定义**项目级列表与用户级列表的层级关系**（覆盖 vs 追加），以及面板上如何表达「这条信任来自哪个目录根」。
- **项目身份不稳的两类案例必须先规范化**，否则候选是垃圾：①同一目录在 git init 前后产生 `path:` / `git:` 两个 key（`~/Projects/zenone-obsidian-vault` 实际如此）；②测试沙箱（`.pi/tmp/files-multi-test-*`、`/private/var/folders/…/agent-proto`）也各自生成 projectKey，它们不是项目。
- 「信任不因同一个仓库自动扩散到别的 worktree」是**刻意保留的边界**，不要当作缺陷「优化」掉。

## 补充（scope 列表化的层级语义与迁移）

**决策**：三级**逐级覆盖**（会话 > 项目 > 用户），未定义则向上继承；**用户级列表是底**。

- 项目级显式写 `scope` = **收紧**，正确地遮蔽用户级（失败即拒绝，是特性不是缺陷）。会话级可临时收紧（在敏感项目里临时只信本目录）。
- **关键配套迁移**：删除「等价于默认值」的项目级 `scope`（值为 `.`，或等于该 cwd 自身）——它们不是决策，是设置面板把默认值落盘了（当前 4 个 worktree 正是此情形）。**不清理，范围提升会被这些 no-op 覆盖静默吞掉**：提升把目录写进用户级列表，而每个 worktree 的项目级 scope 仍只认自己。
- **清理的安全边界（fail-safe，消除本条与前条的规则矛盾）**：仅当删除该 no-op `scope` 后**不会新增无出处条件的受信路径**时才清理。若用户级列表中含有项目目录之外、且**不带 `requireSessionProvenance`** 的根（如手工配置的 `[cwd, /tmp]`），删除项目级 `[cwd]` 会把生效范围静默放宽到该无条件根（fail-open）——此时**保留**项目级条目，由面板标出「项目级遮蔽用户级」，交用户裁决。提升写入的 `[cwd, /tmp（仅本会话创建）]` 因带条件，照常清理。
- **面板必须显示「当前生效的 scope 来自哪一层、是否被上层遮蔽」**，否则「提升点了没反应」会成为长期排查负担。

## 修正（信任可见性由「层」决定，scope 只管「目标范围」）

**本 ADR 初稿把「范围提升」的产物写成「把目录根写进用户级 scope 列表」——这是错的。加目录到 scope 不会让信任跨目录可见。**

原因：pi-state 的**项目层是 per-cwd**（`<cwd>/.pi/extensions-data/<plugin>/state.json`），graduated 计数按目录各存一份；`getRuleCounts()` 只合并当前 cwd 的三层（user/project/session）。在 `worktrees/tool` 里攒的 `tool:rm` 计数，`worktrees/security` 的 cwd **根本读不到**——不管 scope 列表里有没有 tool。

修正后的模型是**两个正交变量**，不可混：

| 变量                    | 回答的问题                           | 取值                              | 是否控制跨目录可见性         |
| ----------------------- | ------------------------------------ | --------------------------------- | ---------------------------- |
| **计数所在层**          | 这条信任在哪可见                     | session / project(per-cwd) / user | 只有 **user 层**跨目录可见   |
| **scope（目标根清单）** | 在这个目录里，信任允许对哪些目标生效 | 目录根列表，默认 `[cwd]`          | 不控制可见性，只控制目标范围 |

于是「提升」有**两类产物**，与需求原话的两半一一对应：

1. **层级提升**（「迁移到用户级」）→ 在**用户层**新建一条**类别化**的放行原则（不是把项目层 cmd-hash 原样搬过去——见 ADR-0058 的 key 可移植性论证）。效果：该信任在**所有目录**可见。
2. **目标范围扩大**（「提升使用的项目范围」）→ 往 scope 的**目标根清单**加一个根（如 `/tmp`、`$TMPDIR`）。效果：让**项目目录之外**的目标（删 /tmp 临时目录）也能用上计数。

**为什么两类都必须有**：`isInScope` 要求 cwd 与所有目标路径都落在 scope 内，`rm -rf /tmp/x` 的目标在 scope 外 → 直接落到确认，**即使 user 层有计数也救不回来**（只有 cmd 键的 `hasGraduatedStrategy` 不过 scope 检查，而它要求整条命令完全一致）。反过来，只加 scope 而不写 user 层，跨 worktree 的信任仍不可见。二者缺一，对应的那半摩擦就治不好。

## 补充（范围条目的形态：根 + 条件；判定链路的唯一改动点）

`dynamicPolicy.scope` 由单个绝对路径改为**根列表**后：

- **判定链路上需要改的只有一处**：`isInScope` 从「单路径包含」改为「任一根包含」。其余全部白捡——`getRuleCounts()` 本就合并用户层（所以把计数迁到用户层即跨目录生效），`moveRuleKey` / `deleteRuleKeyScoped` 已存在（迁层与撤销）。
- **每个根可挂条件**，当前只有一种：**仅限本会话创建的路径**（ADR-0025 第四轴）。该根下的目标必须由本会话命令创建过才自动放行，否则退回询问（失败即拒绝）。
- **为什么条件不是可选项**：因 `checkThreshold` 是 OR 语义（`tool:rm ≥ 3` 即放行任意 `rm`），把 `/tmp` 纳入范围后，**现成规则立刻会放行任意 `rm` 到 `/tmp`**。条件是本设计扩面之后唯一的护栏；卡片上默认勾选（见 ADR-0060 补充）。
- **迁移**：项目级 `scope` 等于该项目自身目录（或 `.`）时，视为等价默认值、**不构成收紧**，迁移时清除；否则范围提升会被这些空操作覆盖静默吞掉。

## 补充（判定语义：cwd 与目标各自独立被覆盖）

实现时发现一个会让本 ADR 主路径失效的细节，必须写清：**cwd 与每个目标路径各自独立地被某个根覆盖即可，不要求落在同一个根内。**

- 若要求"落在同一个根"，则「在项目内工作、删 `/tmp` 临时目录」这条主路径**永远不可能命中**（cwd 在项目根、目标在 /tmp）——范围扩大的整个意义就没了。
- **单根配置下两种语义完全等价**，原行为不变。
- 无目标路径的命令只查 cwd（与单根时代一致），避免"无目标"变成"处处在范围内"。
- 已用测试固化：`cwd=/proj` + `target=/tmp/a` + `roots=[/proj, /tmp]` → 命中。
