# ADR-0063: pi 版本基座——双层固定 + latest 探测（拒绝隐式跟随）

**决策**：把"我们在哪个 pi 版本上做过适配"显式化为**双层基座**（类型层 = `package.json` devDependency + `package-lock.json`；运行层 = CI 实际安装的 pi），两者**必须同版本**且**显式声明**（不再依赖 `scripts/setup-ci.sh` 的 `PIPELINE:-latest` 默认值）。"跟随 latest"的语义收敛为 **不落后 + 不隐式**：由一条**非阻塞的、schedule 触发的 latest 探测 job**（金丝雀分片）承担"早发现"，失败只产出"需要一次基座提升"的信号、不阻塞主流水线；基座提升是一次**显式提交**（同步抬升 lock / PIPELINE 与本轮兼容性修改）。术语见 `CONTEXT.md` 的「pi 版本基座」节。

## 修订：探测 job 暂缓（2026-10-13）

决策 2/4（schedule 触发的 latest 探测 job）**暂不实施**。理由：项目当前尚未到"需要定时任务"的阶段，无人值守的周期性探测带来的维护面（cron 节奏、失败信号渠道、issue 生命周期）大于它现在能挡的风险。

**接受后果（知情）**：「不落后」这一诉求暂由**人工/按需**承担——发版轮或察觉到上游变更时手动探测。手动探测的成本已被本 ADR 的实现压到最低：

```bash
# 手动探测 latest（不阻塞任何流水线；PIPELINE 是显式覆盖开关）
PIPELINE=latest bash test/e2e/scripts/run-e2e.sh --shard 0/8
# summary.json 的 pi_version 会记录本次实际跑的版本，便于对比基座
```

**恢复条件**：出现「上游发版后我们长时间没察觉」的实际损失，或模块/回归面大到人工探测不可行时，再启用决策 2/4（本 ADR 的其余决策不受影响）。

## 已知的 1.2.0 破坏面（基座提升的待修项）

**已验证**（差分实测，2026-10-13）：

- `test/vitest/extensions/worktree.tui.test.ts > /worktree help shows commands` **在 1.2.0 上失败、在 0.84.4 上通过**：
  `PI_BIN=<repo>/node_modules/.bin/pi`（0.84.4）→ `4 passed`；全局 1.2.0 → `1 failed | 3 passed`。
  **根因（2026-10-13 定位，已修）**：既不是扩展回归，也不是启动时序——**pi ≥1.2.0 只把「可见区域」写进输出流**，
  该帮助面板高于 24 行默认视口时，文件头 `Usage:` 从未进入流（0.84.4 会把整段文本都写进流，旧用例因此"碰巧"通过）。
  证据：同一用例给 `rows: 40, columns: 100` → `4 passed`；流里能看到面板命令列表（`widget <on|off>`、`group <list|create|…>`）
  却**零个** `Usage:`。修复 = 该用例放大视口 + 注释说明（1.2.0 基座提升提交）。
  **教训**：断言"流里出现过某文本"的用例，其结论依赖渲染器的视口行为，跨版本升级时要先怀疑这类假设。
  影响（已消除）：`pre-push`（裸 `npm test`，不排除 worktree）曾被它阻塞；`pre-commit` 从未受影响（排除 `worktree*.test.ts`）。
- 同一实测顺带证明：**本地 `npm test` 的 TUI 用例跑的是全局 1.2.0**，即决策 7 要修的口径。

**待验证**（1.2.0 的破坏性变更清单，按 dist/文档读出的候选，尚未逐条实测）：

## 被拒方案

- **字面跟随**（类型层也 `@latest`，CI 每次覆盖 lock）：两层一致，但 lock 每次漂移、`npm ci` 失去意义、绿/红不可 bisect——与本仓 ADR-0045 的哨兵/预算/确定性分片所依赖的"可归因"前提冲突。
- **纯显式基座、不做探测**：不落后的诉求无人承担，退化为"等人记得升"或"等 CI 突然红"。
- **维持现状（隐式 latest）**：既不固定、也不留痕，是三种里最差的一种。

## 后果

- 需要新增一条 `schedule` workflow（仓库目前**没有任何** schedule job），并把它与主 e2e 的入口/产物格式对齐。
- 基座提升会成为一次改动 `package-lock.json` 的提交；升级窗口内，探测 job 会持续报"版本落后"，这是预期信号而非故障。
- 主流水线的绿重新变得可复现：同一 commit + 同一基座 → 同一结果。
- 类型层与运行层被**永久绑定**（同一来源）→ 想测"新版运行 + 旧版类型"只有探测 job 一条路；主流水线的 pi 版本只在基座提升时变化，**不随 upstream 漂移**（这正是要的可复现性）。
- `devDependencies` 的 `^0.84.4` 范围会误导（看起来可自动升）；基座提升时应改精确 pin 或注释"以 lock 为准"，否则会出现第三种漂移（devDep ≠ lock）。

## 验证要求（语义级；仅「无报错 / 退出码」不算）

- 当探测到的最新版 **等于**基座时，探测 job 必须"无事发生"地通过（不产生假信号）。
- 当最新版 **高于**基座时，探测 job 必须产出可读信号（含具体版本号与失败用例），且**不得**阻塞主流水线。
- 基座提升提交后，主流水线 e2e 在同一 commit 上重复跑两次结果一致（可复现）。
- 每次 e2e 运行都能从 CI 日志与 `summary.json` 读到本次实际运行的 pi 版本（留痕口径见决策 5）。
- 留痕口径须覆盖**两个**基座消费者：e2e 运行器（`summary.json` 的 `pi_version`）与 vitest node-pty TUI 用例（至少把 `resolvePiBin()` 选中的路径/版本打进测试输出），否则"这个红是哪个版本造成的"仍无法归因。
- 基座提升的**两轮差集只对 e2e 有意义**（e2e 不消费类型基座）；vitest TUI 用例的版本由 `PI_BIN`/`resolvePiBin()` 决定，提升时需单独以新基座跑一遍（含把 worktree 回归作为第一个待修项验证）。
- 留痕实现必须绕开 guard 的硬失败路径：用 runner 已解析的 `"$E2E_REAL_PI" --version`，不得直接 `pi --version`（runner 顶部 `E2E_MODULE_AGENT_DIR` 尚未设置，shim 会走 `${E2E_MODULE_AGENT_DIR:?}` 硬失败且不输出内容）。
- **基座提升必须跑两轮并做差集归因**：提升前用**旧基座**跑一次基线（记录 FAIL 集合）→ 提升 → 再跑一次；两轮差集才可归因到"运行层新版本"还是"类型基座提升"。门禁 = **零 FAIL + 零预算超标**；`[REVIEW]`/`SKIP` 允许存在，但必须逐条留结论（对齐 AGENTS.md 的衡量要求）。提升后再补基线已不可能（运行层随 lock 一起变），所以基线必须**先跑**。
