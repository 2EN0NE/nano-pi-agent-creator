# ADR-0052：成员动态（看板里的"某成员最近在干什么"）

- **状态**：已定（决策收敛 2026-09-14；实现见 `.scratch/org-observe-and-intervene/issues/`）
- **日期**：2026-09-14
- **相关**：ADR-0040（在岗/存活/忙碌与四态 `D5` 单一裁定）、ADR-0041（人类操作台永远可用）、ADR-0043（在岗判据与状态栏）、ADR-0044（成员消息来源）、ADR-0048（唤醒授权与门禁）、ADR-0051（成员启动参数）

## 背景

org 是**多进程编排**：成员是各自独立的 `pi` 进程，跑在 tmux 里，org 只能从**外面**观测它们。当前人类在 TUI 看板能看到的只有两类信息：

1. **「可感知状态」四态**（睡眠 / 空闲 / 工作中 / 待验收）——回答"在不在、忙不忙"；
2. **任务账本**——回答"有什么活、走到哪一步了"。

两者都**不回答"这个成员现在到底在干什么"**。真实痛点（2026-09-14 人反馈）：派活之后只能看着"工作中"这个状态干等，无法判断成员是在正确推进、还是卡住/跑偏了。

对照参考：`@quintinshaw/pi-dynamic-workflows`（workflow 插件）在同类问题上体验很好——它的 agent 详情页对**活动中的 agent 显示 prompt + 最近 2 条事件**，pager 支持 `t` 实时跟读。但它的"看得见"是**架构红利**：它自己 spawn/host 子 agent，事件流天然在手里（`compactAgentHistory(session.messages)`，`src/agent.ts:1052`），压缩后随运行态落盘（`PersistedAgentState.history`，`src/run-persistence.ts:36`，注释明确"不存完整 transcript"）。org 搬不了这套实现，只能跨进程取——但**可取，且可抄件齐全**（见「复用清单」）。

## 决策

### D1：数据源 = 在岗成员进程的 control 控制 socket 新增 `get_history` RPC（已定）

- control 扩展已跑在**成员进程内**，能拿到该会话的完整消息分支（`ctx.sessionManager.getBranch()`）——这与既有 `get_message`（返回最后一条 assistant 文本，`extensions/auto/control/index.ts:632`，实现 `:458`）同源同款，属**同模式扩展**，不是新机制。
- 返回内容为**压缩后的事件行**：`{role, kind: text|toolCall|toolResult|error, text, toolName?, diff?, timestamp}`——形状与压缩口径照抄 workflow 的 `compactAgentHistory()`（`@quintinshaw/pi-dynamic-workflows/src/agent-history.ts:28`，纯函数、已导出），org 侧只需渲染。
- **否决**：org 自己读成员会话 JSONL（`~/.pi/agent/sessions/<slug>/<file>.jsonl`）——零协议改动的诱惑很大，但要处理三个坑：① 当前会话文件定位（续接 `--session-id` 后文件名/时间戳与 runtime 记录的关系）；② 增量写入的半行/未 flush；③ 拿不到"正在流式输出但尚未落盘"的部分。**否决** `get_summary`（control 的另一条命令，:643）：它要调 LLM 做摘要，成本与延迟都不适合看板轮询。

### D2：纯只读观测，不参与判定、不进账本、不受门禁（已定）

- **不参与「可感知状态」判定**（ADR-0040 `D5` 单一裁定）：动态取不到 ≠ 成员不在岗；四态的唯一判据仍是「runtime 记录 + socket 可连 + 本会话已上岗」。
- **不进任务账本**：它是"看一眼"的观测面，不是事实来源；账本仍是任务的唯一权威。
- **不受唤醒门禁约束**（ADR-0048）：读动态不是唤醒动作，与 `autoWake` 无关；不产生任何副作用（与「巡检」的"感知与动作分离"同精神）。
- **失败即降级**：socket 不可连 / 超时 / 老版本 control 不认这条命令 → 显示「（无动态）」，**绝不弹错、绝不影响四态显示与派活**。

### D3：只在人类看板打开期间拉取（已定）

- 复用既有「巡检」生命周期（`board.ts:334-346`：`setInterval(PRESENCE_POLL_MS=4000)`，"看板打开期间运行，关闭即停"）；**不做后台常驻轮询、不落盘、不进会话**。
- 依据：该信息只服务于"正在看板的人"；关掉看板即无人消费，没有必要付出任何成本。

### D4：拉取范围与频率 = 混合（列表快照 + 详情跟读）（已定，2026-09-14）

- **列表页（成员视角）**：进入该视角时对**在岗**成员各拉 **1 条**（最近一条文本摘要），此后随巡检（4s）刷新；未在岗成员恒定「（无动态）」，不发 RPC。
- **详情页（选中成员）**：对当前选中成员拉最近 ~10 条事件，每 tick 刷新 → 提供 workflow 式的"跟读"感。
- 理由："每行都活"在 4s 节拍下会变成视觉噪声与整屏重绘抖动；人的诉求是"**大概**知道在干啥"——列表给"最近一句话"、详情给"最近一串事件"正好匹配。

### D5：RPC 带 `limit`，截断口径由 org 定（已定方向）

- `get_history` 接受 `limit`（要几条），**不允许无上限拉取**：即使照抄参考实现的三重上限（40 条 / 单条 2000 字符 / 总量 20000），全员逐 tick 全量拉也会到 `~80KB × N / 4s`——列表页只要 1 条就没有这个问题。
- 单条与总量的具体数值在实现票中定；口径参照参考实现（其余照抄 `compactAgentHistory` 的截断策略）。

### D6：人类"去看原始明细"的入口要写在界面上（已定需求，呈现细节待定）

- 事实基础：看板**已经**算出 `tmuxManaged`（`board.ts:191-192,300-302`，随巡检刷新），成员详情屏诊断行也已显示 `tmux <会话名>` 或 `手工启动`（`board.ts:1352-1359`）——"这个成员有没有 tmux 会话"是现成的据实信息，**零新增成本**。
- 需求：footer 必须让人类一眼知道**如何进入该成员的 tmux 会话看原始明细**（`tmux attach -t <会话名>`，并提示如何退出）。
- **据实约束**：仅对 **tmux 托管**成员提示该命令；`手工启动`的成员不得给出无效命令。
- 呈现细节（放列表页还是详情页、长命令还是短命令、宽度不足时丢谁）见 `D7`（已定：详情屏诊断行）。

### D7：tmux 入口 = 成员详情屏诊断行改写为可执行命令（已定，2026-09-14）

- 形态：详情屏诊断行由 `在岗 12m · tmux org-dev-team-worker-a · 会话 01a09d…` 改为
  `在岗 12m · tmux attach -t org-dev-team-worker-a（Ctrl-b d 返回）· 会话 01a09d…`——**据实**（仅 tmux 托管成员；`手工启动`的成员保持原样，绝不给无效命令）。
- **列表页 footer 不加**：实测（`visibleWidth`，CJK 记 2）列表 footer **已达 78**，带上现有 hint（`p 启动参数`/`f 自动唤醒`）为 **108**——80 列下本就在截断，任何新增都会被 `truncateToWidth` 砍掉尾部（砍掉的正是现有提示）。详情 footer 仅 26，但也装不下完整命令＋退出提示（会到 81）。
- 理由：详情屏诊断行**本来就在显示会话名**，改成可复制执行的命令不占 footer、不增行数、零新增成本。

### D7b：列表页 = 每个成员下方一行摘要（已定，2026-09-14）

- 形态：成员主行**保留**（名称 / 标记 / `fitDir` 目录 / `dirGone` 提示），其下缩进一行淡色摘要：`14:32 正在改 preset 的 applyTools 覆写…`（截断到可用宽度）。
- 理由：`dir` 与 `dirGone` 是**有诊断价值的既有元素**（`board.ts:934-940`：成员目录被清理时要显示出来），不该为摘要让位；每成员两行在 ≤5 人时容量无压力；每 tick N 条 RPC（每人 `limit=1`）成本可忽略。
- 退路：成员数多到滚动吃力时，退化为"仅选中成员一行"。

## 范围外（另立 ADR）

**人工干预在岗成员的执行**（人反馈 2026-09-14）：暂停当前 loop（abort）→ 人再决定重派任务 / 重试 / 回退会话树某节点后重新下指令。挂点已核实：

- turn 级中断**现成**：control 已有 `abort` 命令（`ctx.abort()`，`extensions/auto/control/index.ts:602`）；
- 会话树回退**有先例**：control 内已用过 `sessionManager.rewindTo(entryId)`（`:739-744`，压缩路径）；
- 分叉**有 API**：pi 扩展提供 `ctx.fork(entryId, { position })`（`docs/extensions.md:1172`）。

但这是**动作/控制域**（与 ADR-0040「感知与动作分离」、ADR-0048 唤醒门禁同族），不属于"只读观测"的本 ADR；其权限、门禁与幂等口径另立 [ADR-0053](./0053-human-intervention-on-duty-members.md) 讨论。

**分批决定（2026-09-14）**：与「成员动态」同批做 A（轮级中断）+ C（任务层重试/重派）；**B（会话树回退/分叉）本批不做**——过渡手段是用本 ADR `D7` 的 `tmux attach` 提示进成员终端，用 pi 自带的 `/tree` 手动处理。B 的远端化另立票。

### D8：降级口径（已定，2026-09-14）

- 成员进程跑**旧版 control**（不认 `get_history`）→ 该成员的动态恒显示「（无动态）」，**静默降级**：不弹错、不影响四态显示与派活；**首次遇到记一次 `warn`**（含成员名与原因），之后不重复刷日志。
- socket 不可连 / 超时同此口径（与「巡检」的只读性质一致：观测失败绝不升级为状态或动作）。

## 备选与否决

| 方案                                                 | 否决理由                                                                                  |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 把动态并入「可感知状态」（如新增第五态"正在改文件"） | 违反 ADR-0040 `D5` 的单一裁定，"在干什么"与"在不在"是两条正交轴；混进四态会让门控判据漂移 |
| org 读会话 JSONL 文件                                | 见 `D1`：定位 / 半行 / flush 三个坑，且实时性更差                                         |
| 常驻后台轮询并缓存                                   | 无人消费时的纯浪费；且引入"缓存过期/多实例"的额外状态                                     |
| `get_summary`（LLM 摘要）                            | 每次轮询一次模型调用，成本与延迟不可接受                                                  |

## 验证方式（tickets 阶段细化）

1. **vitest（组件/单元）**：事件压缩与渲染（空动态 / 工具调用 / 超长截断 / `limit` 生效）；RPC 失败与"命令不认得"的降级路径不改变四态。
2. **e2e（真实多进程，仅 mock LLM）**：真实成员进程产生若干轮事件后，看板能显示其动态；成员进程为旧版 control（不认 `get_history`）时降级且不报错。
3. **TUI（headless）**：多宽度下不超宽；列表页与详情页形态；跟读刷新不引发超宽/抖动（对齐 ADR-0023 与 TUI 测试强制要求）。
