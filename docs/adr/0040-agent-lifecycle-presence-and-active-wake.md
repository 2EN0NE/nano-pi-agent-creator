# ADR-0040: 成员进程生命周期治理——可感知状态与主动唤醒

- 状态：**已落地**（2026-09-10 起实现推进；2026-09-13 收口——「待定」除「巡检阈值校准」外均已落地）
- 相关组件：`extensions/auto/org`（`board.ts` / `index.ts` / `orgstore.ts` / `dispatch.ts`）、`extensions/auto/control`（控制 socket = 在岗判定前提）、`tmux`（唤醒宿主）
- 延伸：落实 ADR-0038 `D5 唤醒机制`（「spawn 为主 + inbox 兜底」）中**从未落地**的那一半；修订 ADR-0039 §I 的两条人员展示条目；补充 `CONTEXT.md` 术语
- 术语：见 `CONTEXT.md`（多 agent 框架节：可感知状态 / 主动唤醒 / 睡眠 / 巡检 / 唤醒入口 / autoWake）

## 背景

org 框架里"成员离线"目前只有一条处理路径：派发时目标 socket 不可连 → **落 `inbox/` 持久化**（任务不丢），等**成员自己的 pi 下次启动**时补投。也就是说：

- **任务不丢，但对方不会动**——真正让成员跑起来的一直是"人手工去那个目录启动 `pi --session-control`"（`org-member/SKILL.md:10-12`、`org-recover/SKILL.md:20` 都这么写）。
- `extensions/auto/org/*.ts` 里**零** `spawn`/`child_process`/`tmux` 调用——**没有任何唤醒能力**。
- ADR-0038 决策表 `D5` 写的是「唤醒机制：**总决策 spawn 为主** + inbox 兜底」，但这一行**既未落地、也没像同表其他未落地项那样标 `⏳ 待续`** → 文档比实现"承诺"得更多。
- 反过来，「唤醒依赖人类启动」这个**实际边界从未被任何 ADR 显式记录**——只在技能文档里隐含。

本 ADR 补上：① 可感知状态（presence）的判定与展示；② 主动唤醒（spawn）/ 睡眠（stop）两个进程生命周期动作；③ 与之配套的权限、幂等、续接规则。

## 决策

### D1 唤醒形态 = TUI + tmux

`tmux new-session -d -s org-<公司>-<成员>`，在其中运行 `pi -a --session-control [--session-id <上次>] <该成员的启动参数>`。

> **修订（2026-09-14，见 ADR-0051 D1/D3）**：这里的命令行已不是完整形态——固定核之后还会追加
> 该成员的启动参数（默认 `--no-permission-gate`；加入时写入成员记录，成员记录为唯一真值）。

理由：三种形态只有它能同时满足**独立常驻** + **人类可观察**（可 `tmux attach` 直接看成员干活）——而这正是 ADR-0038「独立存在、按需唤醒」与项目原则「可观测是首要前提」的要求。rpc 形态因 F3 退化为"成员附属于 spawner 的 pi"，与框架定位冲突，不采用；`-p` 一轮即退，不适用。

### D2 唤醒权限 = 人类（TUI 看板）+ 该 org 负责人 agent

- 人类：看板显式操作；负责人：派活时自动（见 D3/D8）。
- **杀停（stop）仍限人类**——唤醒与杀停**不对称授权**（唤醒是可恢复的正向动作；杀停会打断他人进程）。此决定修订 `CONTEXT.md`「死机判定/健康检查」条与 TODO「死机处理」项中「agent 不主动发起 kill」的表述边界。

### D3 唤醒入口只有两个：派活（自动）与看板（人工）

- 「自动唤醒」= **负责人派活时**，若感知到目标成员睡眠且该 org 的 `autoWake` 开启 → 先唤醒再投递。
- 「人工唤醒」= 人类在看板对选中成员显式操作。

> **收紧（2026-09-13 grilling 定）**：`autoWake` 是**「自主 / 命令」唤醒的总门**，不是"派活时的便利开关"。
>
> - **开** = 允许自主唤醒：派活时自动唤醒 + 显式唤醒动作（agent 工具 / 命令）均可；
> - **关** = **不存在任何自主或命令唤醒路径**——agent 工具、`/org …` 命令、派活自动**一律不得唤醒**；成员保持下线，任务落 inbox 兜底，agent 应**停下来请人处理**（走面人通道，ADR-0047）；
> - **唯一例外**：人类在 TUI 看板对选中成员的**当面操作**（`w` 唤醒 / `s` 睡眠）**不受开关约束**（依 ADR-0041「人类操作台永远可用」，否则自锁）；
> - **改开关仅限人类**（TUI 设置页）；agent 不自行开开关。
>
> 语义要点：开关表达的是「**不要自主叫他起来**」，**不是**「成员绝对不可被叫醒」。
>
> 上述收紧已于 2026-09-13 正式化为 **ADR-0048**（其 `D1`–`D8`），本 ADR 的 `D3` 以 ADR-0048 为准。

### D4 巡检（presence polling）只感知，无副作用

看板打开期间用 `setInterval` 轮询，**仅刷新三态显示**；**不唤醒、不杀停**。关闭看板即停。原则：**感知与动作分离**——感知循环里绝不写副作用。(F1 使轮询成为可能；此前因"定时器不可用"的误判，board 采用"打开加载一次 + `r` 手动刷新"的快照式。)

### D5 可感知状态四态 + 圆点映射（派生，零新指标）

| 状态               | 圆点                         | 判定                                                                  |
| ------------------ | ---------------------------- | --------------------------------------------------------------------- |
| **睡眠**           | `th.dim('○')`（暗空心）      | `runtime/<成员>.json` 不存在，**或**其 `socketPath` 不可连            |
| **空闲**           | `'○'`（默认前景色）          | 在岗（socket 可连）且 `busy === false`，且名下无 `delivered` 参与者项 |
| **工作中**         | `th.accent('●')`（高亮实心） | 在岗且 `busy === true`                                                |
| **完成工作待验收** | `'●'`（默认前景色）          | 在岗、`busy === false`，且名下有 `delivered` 参与者项                 |

- **优先级（2026-09-10 定）**：**睡眠 > 工作中 > 待验收 > 空闲**。理由：`busy=true` 是"此刻正在跑"的实时信号，若被"待验收"盖住，人会把"它在忙"误读成"它在等你验收"（最易误判的组合）；反之则长期在忙的成员**永远显示不出"工作中"**，高亮圆点作废。待验收信息不丢——任务视角 `[3 WAITING]` 子 tab 是全局视图，圆点只是成员维度的补充信号。
- **颜色一律走主题 token，禁止写死颜色**：`BoardTheme`（`board.ts:50-59`）提供 `dim / bold / accent / success / warning / error / muted / selectedBg`。「暗」用 `dim`（对齐 `docs/tui-design-principles.md` §271-280「次要/禁用 → dim/muted」），「高亮」用 `accent`（与 §I 负责人 `[负责人]` 标识同色）；「正常」= 默认前景色（不套色）。门禁 `hardcoded-ansi-color`（`check-tui-compliance.ts:92`）会拦截硬编码 ANSI 颜色。
- **「完成工作待验收」可检出**：参与者态机含 `delivered`（`task.ts:140-141`，界面文案「已交付」）；且看板**已缓存**每个 org 的全量任务（`OrgSnapshot = { org, tasks[] }`，`board.ts:94-98`）→ **零新增 I/O**。作用域 = **当前组织**（看板一次只显示一个 org）。

- **圆点字符已核实可用**（2026-09-10）：`●`(U+25CF) / `○`(U+25CB) **不在**门禁拦截范围（`check-tui-compliance.ts:44` 只拦 `Extended_Pictographic`，实测 `npm run lint:tui` 通过），`visibleWidth('●') === 1`（**不触发** `Rendered line exceeds terminal width`）；本仓库已有先例（`pi-session-tree/ui/panel.ts:731`、`permission-gate/confirm-tree.ts`、`tui/answer.ts`）。残余风险仅为 EAW = Ambiguous 终端的**视觉** 1 列偏移（每行最多一个圆点、位置固定，不累积）。

### D6 睡眠是瞬态，不构成豁免

睡眠 = "手动释放资源"；**不引入持久"钉住"标记**。`autoWake` 开启时，负责人派活即把睡眠成员唤醒——这正是该开关的语义。要长期保持下线，关掉 `autoWake` 即可。
（避免新增"声明状态"轴：与"进程状态"叠加会让三态显示产生歧义。）

### D7 判定可靠性：socket 存活 + 巡检清理 stale（阈值待校准）

- 判定以 **socket 存活**为准（F5/F6）；`pid` 仅作杀停用途，**不用 pid 判活**（复用不可靠）。
- 巡检发现某成员**判为睡眠**时，**清掉其残留 runtime 文件**（SIGKILL 时 `clearRuntime` 跑不到），让数据自洽。
- **带年龄阈值**（初版取 30s，`updatedAt` 距今更近者视为"启动中"跳过）——避免误删刚 `registerRuntime`、socket 未起的活注册。**该阈值需真实数据校准**（`先试试`）。

### D8 `autoWake` 按公司存储

存于 `~/.pi/org/<公司>/org.json` 的 `settings.autoWake`，**作用域 = 该组织**（多公司可各自开关）。设置页文案需标注「（本组织）」。
不放不进**插件配置**（`extensions-data/<插件>/config.json` 是用户/项目级、每插件一份，表达不了「每组织一份」）；且负责人派活时需读“目标成员所属 org”的策略。放于 org 目录内使 `renameOrg` 的目录 rename 自动覆盖，迁移清单无需增项。

### D9 幂等与单进程保证（ADR-0038「一目录 = 一员工，单进程在岗」）

1. `runtime` socket 可连 → **跳过**（这条同时覆盖"人类手工在终端启动的成员"——那种情况没有 tmux 名）；
2. 否则 `tmux has-session -t org-<公司>-<成员>` 存在 → **跳过**（F4：tmux 创建是即时的、重名被拒，故封死"spawn 后 1–3s 才注册"的竞态窗口，**无需锁文件**）；
3. 否则 spawn；
4. **自我排除**：目标目录 == 本进程所在目录 → **拒绝**（否则一次唤醒就在人的看板目录里再起一个**该成员的在岗进程**，与人的会话抢同一份在岗状态）。

> **修订（2026-09-11，见 ADR-0041 `D4`/`D6`）**：本条的隐含前提由「一目录 = 一员工 ⇒ 单进程」放宽为「**一目录可多 pi，其中带 `--session-control` 的那个才是该成员的在岗进程**」。由此：第 2 条 `process-alive` 守卫的语义**收窄为陈旧 runtime**（未在岗的普通 pi 不再写 runtime，故不再落入该状态）；第 4 条的理由改写如上。

### D10 睡眠（stop）的执行

- **tmux 优先**：存在 `org-<公司>-<成员>` session → `tmux kill-session`；
- **否则 PID 回退**：读 `runtime.pid` → `kill <pid>`（覆盖**人类手工启动**的成员——当前全部成员都是这种）；
- **杀之前先读 `runtime.sessionId` 并持久化**（见 D11），**不依赖进程优雅退出**；
- **二次确认**（沿用 board 既有惯例）；若该成员 `busy === true` **额外警示**「正在处理任务，中断可能丢弃上下文」；
- **无角色保护**：睡眠不破坏组织数据，负责人自己也可睡（与"负责人不可踢退/最后一名不可踢退"那类**数据破坏性**护栏不同）。

### D11 lastSessionId 持久化与续接

- **位置**：`~/.pi/org/<公司>/last-session/<成员>.json`，字段 `{sessionId, stoppedAt}`。
    - 与 `runtime/`、`inbox/`、`history/` 同构（一成员一文件、按成员名索引）；
    - 不写 `org.json`（那是花名册，`joinOrg/leaveOrg/transferChief` 都在写；**注**：§G 的乐观锁只覆盖任务账本 `saveTask`，`org.json` 的写入无并发守卫，且本 ADR 之后又新增了「在岗注册回写简档 / 设置页改 autoWake / 改组织背景」等写者，多进程并发读-改-写存在丢更新窗口——故 last-session 另置一文件，不参与该文件的竞争）；
    - 不复用 `history/<成员>.json`（那是**离开档案**，语义/频率都不同）。
- **续接**：`pi --session-id <id>`——`pi --help` 语义为「精确的项目会话 ID，**缺失则创建**」，天然给出"正常续接 / 会话已不存在则新建"的降级行为。
- 进程正常退出（`clearRuntime`）**不**自动写 last-session；只有**人类睡眠**这一显式动作写入（避免把每次正常退出都变成一次持久化写）。

### D12 看板展示层（成员视角）

#### ① 圆点在成员行中的位置（2026-09-10 定）

- **圆点在成员行中的位置（2026-09-10 定）**：**行首独立列**，紧跟 `>` 选中位——形如 `> ○ chief[负责人]  /dir`。固定 2 列前缀（圆点+空格），`fitDir` 可用宽度统一 `-2`；空态行与溢出提示行缩进同步调整。理由：状态是"一列"信息（人竖着扫"谁在忙"），且不因名字/`[负责人]` 长度导致圆点漂移。
    - 参考先例 `/custom-session-tree`（`extensions/meta/pi-session-tree/ui/panel.ts:727-736`）的 gutter 是 **2 列固定字段** `th.accent('●')` + 光标位（**圆点在前**）；本面板为与**同一看板内**的任务/设置/候选列表（`>` 恒在第 0 列）对齐，**保持光标在前**。

#### ② 成员详情屏：状态内嵌标题行 + 诊断行（2026-09-10 定）

现状标题行 `成员 chief  派发 3 · 接收 2`（`board.ts:655`）→ 改为：

```text
成员 chief  ● 工作中  派发 3 · 接收 2      ← 标题行：状态 = 圆点 + 状态词
  pid 4821 · 在岗 12m · tmux org-dev-team-chief · 会话 0192a…   ← 诊断行（dim）
```

- 选 C（内嵌标题行 + 诊断行）：详情屏已有「派发 / 接收」**两个各自独立窗口**的区块，行预算紧，故状态**不另起区块**；但诊断信息确有排障价值（"显示工作中却没动静"、"睡眠时该 `kill-session` 还是 `kill pid`"），故**多花一行**专门承载。
- **诊断行内容按在岗/睡眠两态据实**（不显示不存在的字段）：
    - 在岗：`pid <pid> · 在岗 <时长> · tmux <会话名> / 手工启动 · 会话 <sessionId 前 6 位>…`
    - 睡眠：`已睡眠 · 上次会话 <sessionId 前 6 位>…`（无 `last-session` 记录时显示 `已睡眠 · 无历史会话`）
- 超宽由 `truncateToWidth` 保前段（`pid`/时长最要紧）；诊断行整体用 `th.dim`，状态词用与圆点一致的主题色。
- `tmux <名>` 便于人直接 `tmux attach -t <名>` 观察成员；`手工启动` 表明该成员不在 tmux 托管下（睡眠时走 PID 路径，见 D10）。

#### ③ footer「唤醒 / 睡眠」键位（2026-09-10 定）

- **键位**：`w` **唤醒** / `s` **睡眠**（已核实未被占用——现有单键动作为 `a d g m n r x y`，导航 `j k`）。
- **按态只显示可用者**：睡眠时 footer 出 `w 唤醒`；在岗时出 `s 睡眠`；**不同时显示两个**（沿用 ADR-0039 §I「footer 逐屏据实」，避免"按了没反应"）。
- **两屏均可用**：成员列表（当前选中行）与成员详情（当前成员）。
- **确认策略**：睡眠 → 二次确认屏（D10）；唤醒 → 直接执行（幂等跳过 / 失败给出提示）。
- **反馈呈现**：**新增通用提示字段**，不改造既有 `loadError`（后者承载加载与操作错误、已有 error 色语义，改写会波及其全部调用点）。提示行占用行预算 → 出现时须相应压低列表窗口，维持**铁律 1**（组件总高 ≤ 视口）。
- **否决的备选**：单键切换（`w` 一键两义）——同一按键在不同时刻产生**相反**后果，其中睡眠是破坏性的（打断对方 turn），误按代价不对称，不值得省一个键。

### D13 睡眠同样自我豁免

目标目录 == 本进程目录时**拒绝睡眠**——停掉自己所在的 pi 等于自杀式操作（看板会随之中断，且无任何提示）。人类要下线直接退出自己的 pi 即可。与唤醒侧同源（一目录 = 一员工）。

### D14 巡检同时**只读重读账本**（看板与同伴进程写的一致性，2026-09-15 追加）

**问题**：巡检原先只刷三态（+ 后来的成员动态、执行槽），**账本快照只在按键 / 切 org / 自己执行动作后重读**。于是成员在**另一个进程**里认领/交付、巡检标记逾期、派发人改派之后，屏上"成员动态"是新的（走 RPC），任务与参与者状态却停在打开看板那一刻——人看到"成员在干活，任务还写着待领取"。

**决策**：巡检拍**同时只读重读当前 org 的账本**（`listTasks`），内容有变（指纹变了）才重绘：

- 仍是**只读**：不写任何文件，不违反 `D4`「感知与动作分离」；
- **按 `task.id` 保持选中行**：列表按 `updatedAt` 排序，交付/改派都会重排，沿用旧行号会把光标落到别的任务上；只有当原任务**已移出当前状态子 tab**（例如刚被认领：待处理 → 进行中）时才夹紧索引；
- 指纹（`id:status:updatedAt:history 长度`）未变则**不重绘**，避免每拍无意义重排屏幕；
- 与 `refreshActivity` 同款**在途守卫**：上一拍重读未完成则跳过本轮。

**否决的备选**：由成员进程经 control socket **推**事件给看板——跨进程需要新增订阅面，且看板不在场（未打开 / 已关闭）时无人接收，复杂度不抵收益。
