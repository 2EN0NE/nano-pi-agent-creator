# ADR-0041: 在岗门控——org 能力与在岗痕迹绑定

- 状态：**已接受**（2026-09-11）
- 相关组件：`extensions/auto/org`（`index.ts` 生命周期与工具注册、`lifecycle.ts` 唤醒守卫、`board.ts`）、`extensions/auto/control`（`--session-control` flag 的提供者）、`scripts/sync-to-local-pi.ts`（内嵌技能分发）
- 延伸：**修订 ADR-0040** 的 `D9-2`（唤醒幂等的理由文案）与 `B3`（诊断语义）；界定 ADR-0038「一目录 = 一员工」在**多进程**场景下的边界；向 `CONTEXT.md` 补术语
- 术语：见 `CONTEXT.md`（多 agent 框架节：在岗 / org 能力作用域 / 成员简介）

## 背景

`org` 扩展的两类东西原先都在**扩展加载时无条件生效**，与"这个进程是不是本员工在岗的代表"无关：

- `session_start` **无条件**写"在岗注册"（`runtime/<成员>.json`）——只要该 cwd 已加入 org，**任何** pi 进程都算在岗；
- 8 个 LLM 工具（`dispatch_task` / `org_fleet` / `org_my_tasks` / `org_accept` / `org_reject` / `org_claim` / `org_report` / `org_review`）与 3 个内嵌技能**无条件注册**，任何 pi（哪怕只是被 `cd` 进去看一眼）都能看到。

由此产生三个问题：

1. **"注册 cwd" 与 "有进程在岗" 被混为一谈**——`/org join` 之后，任何一次随手 `pi` 都会让该员工"看起来在岗"。
2. **一个 cwd 可以有多个 pi 进程**（真实场景），但它们**写同一个 `runtime/<成员>.json`**（后写覆盖先写），"谁是在岗代表"不确定。
3. **普通 pi（未开 `--session-control`）会写下指向不存在 socket 的 runtime** → 看板判为「睡眠」，而 ADR-0040 `B3` 的 `process-alive` 守卫又因其 pid 存活**永久拒绝唤醒**——该员工再也上不了岗（真 bug）。

## 决策

### D1 在岗判定 = 已注册 org **且** 进程带 `--session-control`

`--session-control` 是 control 扩展注册的 boolean flag，`pi.getFlag('session-control')` 在 `session_start` 内可靠。它是"能收发成员间消息"的**物理前提**，唤醒流程（tmux + `pi -a --session-control`）产出的正是它——复用它是**零新增概念**。

理由的另一半：只有这样，"第 1 步注册 cwd、第 2 步唤醒某个进程"才成为两个可分辨的事实。

### D2 能力与痕迹一起门控

未在岗的 pi **不写 runtime、不注册那 8 个工具、不被贡献 org 技能、不得在岗简报**。原则：**没有 org 能力的进程，不该留 org 痕迹**（技能门控的落地见 ADR-0042 D4）。

### D3 门控只及 LLM 可见面；人类操作台永远可用

门控的是 **agent 的手脚**（工具 / 技能 / 简报），不是 **人类的操作台**（`/org` 命令、`ctx.ui.custom()` 看板）。否则刚 clone 的目录会**自锁**——`/org join`、`/org create`、看板 `w` 唤醒全都进不去，人永远无法把它变成在岗。

### D4 同目录多 pi 合法；"一目录 = 一员工"仍是身份模型

承认"普通 pi + 在岗成员"可在同一目录并存。`一目录 = 一员工（一人格）`管的是**身份**，不是**进程数**。因此 ADR-0040 `D9-2` 与 `lifecycle.ts` 中"否则同一目录会出现两个 pi，直接破坏'一目录 = 一员工'"的理由文案**改写**为：真正要防的是 **org 重复拉起同一个成员的在岗进程**。

### D5 在岗门槛只约束进程级交互

- **需进程配合**（实时收发成员间消息、即时投递）→ 要求在岗；
- **纯数据动作**（踢退 / 设负责人 / 改名 / 改 autoWake / 派活落 inbox 兜底）→ **不要求**在岗。

理由：成员表、任务、设置是**目录级组织数据**，把它门控掉会导致"成员离线时无法增删改"的自相矛盾；且 ADR-0040 `D8` 已把"派活给睡眠成员"（落 inbox 兜底）定为合法路径。

### D6 修订 ADR-0040 `B3` 的语义范围

`process-alive`（进程存活但 socket 不可连）**收窄为陈旧 runtime**（崩溃 / SIGKILL 残留）——普通 pi 不再写 runtime 后，该状态不再涵盖"人类手工起的普通 pi"。看板对陈旧 runtime 的处理（不清理、不重复拉起）不变。

## 后果

- **正向**：在岗语义单一且可判定；"注册了却没人真正在岗"不再被误判为在岗；消除了"普通 pi 让成员永久无法被唤醒"的真 bug。
- **负向**：失去"该目录有进程在跑但收不了消息"的**自动诊断**——普通 pi 不再留痕，看板只显示「睡眠」，此时按 `w` 会在同目录再拉起一个在岗成员。**同目录可能出现两个 agent 并行**（一个普通、一个在岗），由人自行负责。
- **注意**：`board.ts` 已 ~1670 行（pi-lens 标 high-complexity），后续展示层增量需评估是否借机拆分。
