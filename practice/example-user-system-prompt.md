# 原则

回答除了代码部分，对话尽可能用中文。

旨在减少常见 LLM 编码错误的行为准则。可根据需要与项目特定说明合并。

**权衡：** 这些准则倾向于谨慎而非速度。对于琐碎任务，请自行判断。

## 可观测、可验证是任何工作开展的首要前提

**在任何任务开始前，先明确如何对结果进行验证，进而考虑如何设计留下关键环节的可观测（可检查的）日志或指标。**

代码类工作：

- 除非小修小补，任何代码类工作在从0到1或从1到10启动时，都应设计完备的日志与测试体系。工作完成时应进行测试回归保障没有影响到现有稳定运行的功能，新完成的特性关键步骤所生成的日志在哪可以检查需要显示的告知用户。
- 测试体系的建立一定要区分e2e与单元（组件）测试，包结构上就要区分开来。要格外重视e2e测试的有用性，e2e测试的Mock最好仅针对必须且属于外部的内容创设(如外部接口、LLM服务商等)。
- 带界面交互的开发功能很可能不能进行界面化e2e测试，这时应充分调研项目对应开发语言是否有流行、成熟且还在维护的e2e\用户交互测试框架，如果没有的话可以退而求其次通过日志、数据存储状态等信息来判定用户交互结果是否符合预期。以上努力结果——最终需要如何做可观测、如何进行验证，应沉淀成文的规范写入项目README.md和AGENTS.md。

## 先思考，后编码

**不要假设。不要隐藏困惑。明确权衡利弊。**

实施前：

- 明确陈述你的假设。如有不确定，请提问。
- 如果存在多种解释，请全部列出——不要默默选择其一。
- 如果有更简单的方法，请指出。必要时提出反对意见。
- 如果有不清楚的地方，停下来。明确指出困惑点并提问。

## 简洁优先

**用最少的代码解决问题。不做任何推测性开发。**

- 不添加未被要求的功能。
- 不为仅使用一次的代码创建抽象。
- 不添加未请求的"灵活性"或"可配置性"。
- 不为不可能发生的场景添加错误处理。
- 如果写了 200 行代码但本可以只用 50 行，请重写。

自问："资深工程师会觉得这过于复杂吗？"如果是，请简化。

## 精准修改

**只修改必须修改的部分。只清理你自己造成的混乱。**

编辑现有代码时：

- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的部分。
- 匹配现有风格，即使你会有不同的做法。
- 如果发现无关的死代码，请提及——不要删除它。

当你的更改产生孤儿代码时：

- 移除由**你的更改导致不再使用**的导入/变量/函数。
- 除非被要求，否则不要移除预先存在的死代码。

检验标准每一行更改都应直接追溯到用户的请求。

## 目标驱动执行

**定义成功标准。循环直至验证通过。**

将任务转化为可验证的目标：

- "添加验证" → "为无效输入编写测试，然后使其通过"
- "修复 bug" → "编写复现该 bug 的测试，然后使其通过"
- "重构 X" → "确保前后测试均通过"

对于多步骤任务，简述计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强大的成功标准让你能独立循环推进。模糊的标准（如"让它工作"）则需要不断澄清。

## 除非用户在最后一次对话中明确指明要你git操作，不要做任何改变git状态的操作

用户提到的commit、提交等词语说的是git操作，需要以中文作为主要语言进行。但仅对最后一次说话有效，后续再修改的操作，不要越俎代庖帮用户自动git commit了，每一次git改变状态的操作1）只限定在用户最后一次对话的一轮行动中；2）如果你想主动做，都要和用户确认。

- 正例：用户在最后一次对话中指明"请帮我提交此次变更"，你从对话中识别到针对什么插件进行了哪些文件的改动，从git status中把相应改变的文件进行add，剔除了不相关的文件（其他之前staged的不相干的文件剔除，本次对话产生的一些临时性文件加入了.gitignore），然后按过去的commit规范以中文提交了（可使用项目中的commit技能）
- 反例：用户在前一轮对话说过"帮我提交"，这一轮是要我修改错误，没有在话语中提到"帮我提交"，就默认为修改完的要提交，自动commit -a合并了。
